Squeezing the SM: CUDA Performance From the First Kernel to Blackwell

2026-09-13

A kernel is never just slow. It’s slow because it’s waiting for something, and the whole point is finding out what.


Cover image: NVIDIA

It has been a while since my post on Inside the GPU, and there I talked about the hardware: SMs, warps, the memory hierarchy, and that long trip out to global memory. Then in Ahead of the Pipeline-II, I went through the layered system a GPU uses to hide that trip. What neither of my posts answered is the question you run into the moment you write a real kernel: is this fast?

Not “does it run”, and not “is it faster than the CPU”. Is it anywhere near what the hardware can actually do, and if not, what exactly is in the way?

Here’s something that took me a while to appreciate: that question has a precise answer. Once you know how to ask it, CUDA optimisation stops looking like a bag of tricks. Coalescing, shared memory, bank conflicts, occupancy, tensor cores, async copies, FlashAttention: every one of them is an answer to the same small set of physical problems. So rather than splitting this into a series, I wanted all of it in one place, as one connected story.


Six parts, twenty-five chapters. Each part leans on the ones before it.

A few notes on reading it. The chapters are numbered so you can jump around, and on a wide screen the contents sit in the left margin. If you already know how a kernel gets launched and how warps execute, you can skim Part 1 and start at the performance model in chapter 5. Every part ends with a short in short box that recaps it in a paragraph. And every diagram is there to replace a paragraph, not decorate one.

Fair warning: this is long. Grab a coffee. Maybe two.

Part 1: Foundations

Before any optimisation, you need an honest picture of what actually happens: how your source becomes machine code, how work gets launched, how to time it, how a warp really executes, and what “fast” even means for a given kernel. Everything in the later parts builds on these five chapters.

1. From Source to SASS: The Toolchain and Errors

A .cu file looks like one program, but it’s really two programs sharing a file. There’s the host code that runs on the CPU (main, the memory allocations, the kernel launches) and the device code that runs on the GPU (every function marked __global__ or __device__). The first thing nvcc does is pull them apart.


One file, two compilers, two kinds of machine code. The GPU side goes through a virtual instruction set before it becomes the real one.

The host code goes to an ordinary C++ compiler (MSVC, gcc or clang). The device code takes a more interesting route. It’s first compiled to PTX, a virtual instruction set: portable across GPU generations, stable, documented, and not what actually runs. A second tool, ptxas, turns PTX into SASS, the real machine code for one specific architecture.

Both end up packed into the executable as a “fatbinary”, and that detail matters. Compile with -arch=sm_89 and the executable carries SASS that runs directly on that generation, plus the PTX, so a future GPU that has never seen your code can still compile it on the fly when the program starts.

The number in sm_89 is the compute capability, and it’s more than a version label. It decides which instructions exist at all. Asynchronous copies need compute capability 8.0 (Ampere) or newer; warpgroup matrix instructions need 9.0 (Hopper). No compiler flag turns one generation into another, which is why some of the most interesting material later in this post needs specific hardware.

Two compiler habits pay for themselves immediately. -Xptxas -v makes ptxas report, for every kernel, how many registers it uses, how much shared memory, and whether anything spilled out of registers into memory. You’ll see later why those three numbers explain a surprising number of slow kernels. And -lineinfo embeds a map from machine instructions back to your source lines, so the profiler can point at the exact line that’s stalling. You’ll also see names like _Z6vecAddPKfS0_Pfi in tool output: that’s the C++ mangled name of vecAdd(const float*, const float*, float*, int), and every profiler speaks in those.

Errors that arrive late

The first thing that surprises everyone is how errors behave. A kernel launch is asynchronous: kernel<<<blocks, threads>>>() drops the work into a queue and returns immediately, long before the GPU has even started.


The bug happens in the kernel. The error message shows up wherever the CPU next waits for the GPU, which can be far away in the code.

So errors come in two kinds. A launch error, like asking for more threads per block than the hardware allows, is caught right away by cudaGetLastError(). An execution error, like reading past the end of an array, only shows up at the next call that waits for the GPU, which might be a cudaMemcpy several lines or several files away. And some execution errors are sticky: an illegal memory access breaks the whole CUDA context, and every call after it fails until the process restarts.

The cure is boring and essential: check every call.

The really dangerous bugs, though, aren’t the ones that crash. They’re the out-of-bounds reads that don’t crash, because the memory just past your array happens to belong to your program, so you get a plausible-looking wrong answer. Catching those needs compute-sanitizer, which chapter 17 covers.

2. Launching Work: Blocks, Grids, Waves and Grid-Stride Loops

Every thread works out which piece of data it owns from its coordinates:


The grid is rounded up, so the last block usually overshoots. The bounds check is what keeps those extra threads away from memory.

You choose a block size and round the number of blocks up, so for a million and three elements you launch a few hundred threads more than you need. Those extra threads land in the last block, and the if (i < n) is the only thing stopping them from writing past the end of the array. Forget it and, more often than not, nothing visibly breaks. That’s exactly what makes it dangerous.

When the grid is launched, the GPU’s block scheduler hands blocks to SMs as they have room. Once a block lands on an SM it stays there until it finishes: it never migrates, and it can’t be paused to make room for another. Blocks run in any order, which is why threads in different blocks can’t safely wait for each other.

For 2D data you use 2D blocks and grids, and one detail here matters far more than it looks:

The 32 threads the hardware groups into a warp are taken from consecutive thread IDs with x varying fastest. In a row-major matrix, consecutive columns sit next to each other in memory, so x has to map to columns. Swap the two and every warp reads 32 different rows, each a whole row apart in memory: identical results, many times slower. The grid limits aren’t symmetric either. The x dimension allows over two billion blocks, while y and z stop at 65,535, so long dimensions belong on x.

Waves and the tail

If every block takes about the same time, the GPU works through them in waves: as many blocks as fit across all the SMs run together, finish, and the next batch starts. The last wave is usually only partly full, and while it runs, the SMs that got nothing just wait. This is wave quantization, also called the tail effect.


The last wave decides the runtime. Nine blocks cost as much as sixteen, because the ninth needs a whole second wave to itself.

How many blocks make up a wave depends entirely on the chip. NVIDIA’s Turing generation is a good illustration, because it shipped as a family of dies built from the same SM design in different quantities:


Top to bottom: TU116, TU106 and TU104. The same Turing SM, in 24, 36 and 48 copies. Photo: Fritzchens Fritz via Wikimedia Commons, CC0

Launch the same grid of 100 heavy blocks on each, one block per SM at a time. On the 48-SM TU104 that’s three waves, and the last one holds just 4 blocks. On the 36-SM TU106 it’s three waves with 28 in the last. On the 24-SM TU116 it’s five waves, again with only 4 in the last. A launch configuration tuned on one GPU can leave a ragged tail on another, which is why the SM count is the first number worth knowing about any GPU you target.

For a light kernel with thousands of blocks, the tail is one wave out of dozens and you’ll never notice it. It bites when blocks are few and heavy, which is exactly the situation of big matrix multiplies and attention kernels. Take an A100, with 108 SMs, computing a GEMM in 128×128 output tiles, one block per tile and one block per SM at a time. A 1408×1408 output is 11 × 11 = 121 tiles: a full wave of 108, then a second wave of 13 that leaves 95 SMs idle. Overall the GPU is only 56% busy. A 1792×1792 output is 196 tiles, which also takes two waves. So the bigger multiply does 62% more work in roughly the same time.

Real kernels blur this a little, because blocks don’t finish in perfect lockstep, but the effect is very real. It’s why GPU libraries pick tile sizes with the SM count in mind, and why techniques like Stream-K (chapter 20) exist.

Grid-stride loops

There’s a second way to write the same kernel, and you’ll find it all over production code, including PyTorch’s elementwise kernels:


Launch a fixed grid and let each thread loop. Every pass is still a contiguous, coalesced sweep.

Instead of one thread per element, you launch a fixed-size grid and let each thread loop, stepping by the size of the whole grid. It works for any n, even inputs bigger than the largest grid you could launch. It lets you size the grid to the hardware rather than the data: launch exactly one full wave of blocks and there’s no tail at all. Per-thread setup happens once per thread instead of once per element. And launching it with <<<1, 1>>> turns it into a plain serial loop, which is a lovely debugging trick.

One last fact about launches: they aren’t free. Each costs a few microseconds of CPU and driver work before the GPU even starts, more on Windows laptops, where the display driver model batches and delays submissions. For a kernel that runs for milliseconds that’s nothing. For one that runs for three microseconds it’s most of the cost, and a model made of hundreds of tiny kernels can spend more time launching than computing. Hold that thought for CUDA Graphs in chapter 16.

3. Measuring Without Fooling Yourself

Every optimisation from here on is a claim that something got faster, and a claim needs a measurement. GPU measurements are unusually easy to get wrong. To show how much, I ran plain vector add on my laptop’s RTX 4060 in several different ways. Same kernel, same GPU, same afternoon. Its memory can physically deliver 256 GB/s.


Five answers to one question. Only one of them measures what the memory system can actually do.

The CPU clock doesn’t see the GPU. Timing the launch with the CPU clock gave 0.025 ms. Adding a cudaDeviceSynchronize() before stopping the clock gave 3.417 ms. That’s the same kernel, measured 137 times apart, because a launch only submits the work. The right tool is a CUDA event, a marker placed in the same queue as the kernel, which the GPU timestamps on its own clock when it reaches it:

For very short kernels, put many launches between one pair of events and divide, so the fixed costs average out.

The first run pays for everything. The very first CUDA call took 187 ms in one run and 316 ms in the next, while the driver created a context. The first launch of the kernel then cost 20 ms of CPU time against 0.025 ms once warm. Add the fact that an idle laptop GPU parks at low clocks and needs a moment of work to ramp up, and the rule is obvious: run a few times and throw those results away before you measure anything.

The L2 trap. With small 4 MB arrays and nothing else changed, vector add reported between 658 and 791 GB/s, three times what the memory can physically do. Nothing beat physics. The data just wasn’t coming from DRAM. This GPU has a 32 MB L2, and three 4 MB arrays fit comfortably, so after the first run they were still sitting on chip. Flushing L2 between runs brought the same kernel down to 166 GB/s, and only with 256 MB arrays did it settle at an honest 230 to 234 GB/s.

Neither the warm number nor the cold number is wrong. They answer different questions, and the real question is which one matches your workload. An LLM decode step streams gigabytes of weights per token, and those never fit in any cache, so only the cold number is honest. A small activation tensor written by one kernel and read by the next really does live in L2, and there the warm number is realistic. Choose the cache state deliberately, and write down which one you chose.

Turn time into meaning. So the honest number is about 3.45 ms. Is that good? A time in milliseconds can’t tell you. It only becomes meaningful as a rate compared with what the hardware can do:

effective bandwidth = bytes the algorithm must move ÷ time

Three arrays of 64 million floats is about 805 MB in 3.45 ms: 233 GB/s, or 91% of peak. That changes the conversation entirely. A memory-bound kernel at 91% of peak bandwidth is finished; no clever trick makes it meaningfully faster. “It takes 3.45 ms” says nothing. “It’s at 91% of peak” says stop.

You’ll never quite reach 100%, either. DRAM has to refresh, rows have to be opened and closed (the row-buffer penalty from Ahead of the Pipeline-I), and the bus loses time whenever it switches between reading and writing. That’s why the plain cudaMemcpy in the chart only managed 218 GB/s, slower than vector add: a copy is half reads and half writes, so it switches direction more often.

One run proves nothing. Twenty repeats of the big kernel stayed within 3% of each other in one batch. In the next, one of the twenty took 4.53 ms, a third slower, with no change to the code. Laptops share power and cooling between CPU and GPU, and clocks move with temperature. Report the median of many runs, check the spread before trusting a difference, and lock the clocks where you can.

4. How a Warp Actually Runs

You write CUDA from the point of view of a single thread: compute your index, load your element, do your maths. That’s a fiction, and a very productive one. The hardware doesn’t run single threads. It runs warps of 32, and almost every performance rule in this post comes from the gap between the thread you wrote and the warp that actually executes.

An SM is split into four processing blocks, each with its own warp scheduler. Every cycle, each scheduler looks over its warps, picks one that’s ready (an eligible warp), and issues that warp’s next instruction to all 32 threads at once. One instruction fetched and decoded, 32 lanes executing it, each on its own registers and data. That’s SIMT, single instruction, multiple threads.

It helps to see where these SMs physically are. On a die shot of the GA100, the chip inside the A100, they’re impossible to miss:


The GA100 die. Each repeated tile is a streaming multiprocessor: 128 on the full chip, 108 enabled on an A100. Every technique in this post is, in the end, about keeping those tiles busy. Image: Wikimedia Commons, CC BY 3.0

Zoom into one tile and you find the pieces this chapter is about. NVIDIA’s own diagram of the SM from its Fermi generation is older and simpler than today’s (two warp schedulers instead of four), but every part is still recognisable:


NVIDIA’s diagram of a Fermi SM from 2010: two warp schedulers, a register file shared by every resident thread, 32 CUDA cores, load/store units, special function units, and shared memory sharing SRAM with L1. Today’s SMs are bigger, but every one of those pieces is still there. Diagram: NVIDIA via Wikimedia Commons, CC BY 3.0


No warp gets any faster. The scheduler just needs enough of them that someone is always ready.

Most warps, most of the time, aren’t eligible. They’re stalled, waiting for a memory load, for the result of a previous instruction, or at a barrier. The scheduler doesn’t care. It issues from whoever is ready, and switching costs nothing, because every resident warp’s registers stay in the register file the whole time. There’s nothing to save or restore. That’s the entire trick of GPU latency hiding, and the picture above already contains the idea chapter 5 turns into a formula: with too few warps, the issue slots go empty no matter how good each warp’s code is.

Divergence

Now the catch. One instruction, 32 threads. So what happens when they disagree about a branch?

If all 32 threads agree, the warp takes one path and skips the other. If they don’t, the warp can’t do both at once, because it only has one instruction stream. So it runs them one after the other: first path A with an active mask that switches off the threads that wanted B, then path B with the mask flipped, and then everyone reconverges and carries on together.


Both conditions send exactly half the threads down each path. Only one of them costs anything.

That’s warp divergence, and its cost is simple: a divergent warp pays for path A plus path B. Loops diverge too, more quietly. If each thread loops a different number of times, the warp keeps going until its slowest thread finishes. A warp where 31 threads need 10 iterations and one needs 1,000 runs 1,000 iterations.

The single most important thing about divergence is its granularity: it only exists inside a warp. if (threadIdx.x % 2 == 0) splits every warp in half and doubles the cost of the branch. if ((threadIdx.x / 32) % 2 == 0) sends exactly the same number of threads each way and costs nothing extra, because whole warps agree. Same work; only its alignment to warps changed.

Not every if is a branch, either. For short conditionals the compiler often uses predication: it computes a one-bit predicate per thread and issues the instructions of both sides with a guard, so each thread only commits its own side. In machine code you see this as instructions prefixed with @P0. A bounds check or a small x > 0 ? a : b is cheaper this way than branching. What actually hurts is divergence over expensive paths, or loops with wildly different trip counts.

Since the Volta generation there’s one more subtlety. Each thread has its own program counter, so the hardware can interleave divergent paths and reconverge wherever it likes. This independent thread scheduling doesn’t make divergence cheaper, but it means the threads of a warp are no longer guaranteed to run in lockstep. Old code that quietly relied on lockstep became a race condition overnight, which is why every warp-level operation in modern CUDA takes an explicit mask (chapter 11).

The fixes all come down to one idea: make the threads of a warp want the same thing. Sort or bucket the data so neighbours take the same path. Give each warp a category of work instead of each thread. Replace cheap branches with arithmetic. And for loops with very uneven lengths, rebalance the work itself (chapter 12).

5. The Performance Model: How Fast Should This Kernel Be?

This is the chapter the rest of the post hangs off. Before optimising anything, you need to know what’s actually limiting the kernel, and how far it is from the best it could possibly do.

The three walls

There are really only three things a kernel can be up against.

The first is memory bandwidth. The kernel needs to move more bytes between the SMs and DRAM than the memory system can deliver in the time available. Vector add is the purest example: the addition is so cheap that the whole kernel is a race to move bytes.

The second is compute throughput. Every execution unit is busy every cycle, and the kernel simply contains more arithmetic than the chip can do any faster. A well-written matrix multiply ends up here, which is exactly where you want it.

The third one is sneaky: latency. Neither of the first two is saturated. The memory system has bandwidth to spare, the ALUs have idle cycles, and yet the kernel is slow, because the GPU spends most of its time waiting. Most first attempts at a kernel live here, and most people writing them don’t know this wall exists, because no single unit looks overloaded. It isn’t mysterious, though. It has a formula.

The roofline: where the ceiling is

The first two walls fit into one picture. If you read the Tradeoffs post, you’ve already met it: the roofline model. The key quantity is arithmetic intensity, the number of floating-point operations a kernel performs per byte it moves to or from DRAM.

attainable FLOP/s = min( peak FLOP/s , arithmetic intensity × peak bandwidth )

Put an A100’s numbers on it. Its FP32 CUDA cores peak at 19.5 TFLOP/s (108 SMs × 64 cores × 2 FLOPs per fused multiply-add × 1.41 GHz), and its HBM2 delivers 2,039 GB/s. At low intensity, performance climbs along the bandwidth slope. At about 9.6 FLOPs per byte the slope hits the compute ceiling: the ridge point. To its left a kernel is memory-bound, to its right compute-bound, and past it more intensity buys nothing. Those are the specs of this card, and they’ll keep coming back for the rest of the post:


The A100. Its numbers (108 SMs, 19.5 TFLOP/s of FP32, about 2 TB/s of HBM2) are the running example for most of this post. Image: NVIDIA via Wikimedia Commons, CC BY-SA 4.0


Elementwise kernels live at the far left, pinned to the bandwidth slope. Reuse is the only thing that moves a kernel rightward. The red point is the one to worry about: well below its roof, limited by something the roofline can’t see.

Where common kernels land is humbling. Vector add does 1 FLOP for every 12 bytes (read A, read B, write C), an intensity of 0.08, so its ceiling on an A100 is about 0.17 TFLOP/s, under 1% of the chip’s arithmetic. It doesn’t matter. Vector add was never going to be judged on arithmetic, and the only thing that would make it faster is moving fewer bytes. Anything elementwise lives down there.

Matrix multiply is the interesting case. Computed naively, each multiply-add reads one element of A and one of B, two FLOPs for eight bytes, an intensity of 0.25. But every element is used N times across the output, so if you keep data on chip and reuse it, the intensity grows with the reuse. Tile through shared memory and it grows with the tile size; block further into registers and a good GEMM reaches tens of FLOPs per byte, past the ridge. A large part of this post is, quite literally, a walk from left to right along this chart.

When you work out intensity yourself, count the bytes the algorithm must move to and from DRAM, not every load instruction your code happens to issue. Intensity is a property of the algorithm plus the reuse you achieve, which is exactly why tiling changes it.

The roofline tells you where the ceiling is. It says nothing about whether you’re anywhere near it. That red point sits far below its roof with no wall visibly in the way, and that’s where the third wall lives.

Little’s law: the latency wall has a formula

In 1961, John Little published a proof of a result from queueing theory so simple it sounds like it can’t be important:

items in flight = throughput × latency

A coffee shop that serves 10 customers a minute, where each customer spends 3 minutes inside, has 30 customers in the shop on average. It holds for any system in steady state, and it turns out to be the most useful equation in GPU performance.

Apply it to memory. In Inside the GPU the A100’s global memory latency was about 466 cycles, roughly 330 ns, for a quiet memory system. Under heavy load requests queue, so call it around 500 ns. To actually sustain 2 TB/s, the bytes that must have been requested and not yet returned, at every moment, are:

2 TB/s × 500 ns ≈ 1 MB in flight

Spread across 108 SMs, that’s about 9 KB outstanding per SM, all the time. A warp loading one float per thread, perfectly coalesced, requests 128 bytes, so each SM needs roughly 74 warp-sized loads in flight at every instant. An A100 SM can hold at most 64 warps. Sit with that for a second: even at full occupancy, if every warp waits on one load before doing anything else, an A100 can’t keep its memory busy.


Bandwidth is a pipe, latency is its length, and Little’s law says how full it has to be. A half-empty pipe wastes bandwidth no matter how good each individual access is.

This reframes latency hiding completely. Switching between warps is one way to keep enough requests outstanding, but there are exactly two ways to get bytes in flight:

  1. More warps, each with one load outstanding. This is thread-level parallelism, and it’s what occupancy measures.
  2. More work per warp: each thread issues several independent loads before it needs any of the results. This is instruction-level parallelism, and a single float4 load already counts, since one instruction now requests 512 bytes per warp instead of 128.


Little’s law doesn’t care where the in-flight work comes from. Many warps with one load each and a few warps with several loads each fill the pipe equally well.

That was the whole point of Vasily Volkov’s well-known 2010 talk, Better Performance at Lower Occupancy: a kernel with few warps but lots of independent work per thread can beat a kernel with many warps doing one thing at a time. So the latency wall isn’t some vague “the GPU is waiting”. It’s a precise shortfall: not enough independent work in flight to cover the latency at the bandwidth you want.

Occupancy: a means, not a goal

Occupancy is the ratio of warps resident on an SM to the maximum it can hold. It gets talked about as if it were the goal. It isn’t, but it’s worth knowing exactly what limits it.

How many blocks can sit on an SM at once is capped by four resources, whichever runs out first: thread slots (2,048 on an A100), block slots (32), registers (65,536 per SM) and shared memory (up to 164 KB). Registers come with cliffs, and chapter 8 is about them. Block size has its own trap, and it depends on the GPU. RTX 30 and 40 series SMs hold 1,536 threads rather than 2,048:


1024-thread blocks look like the efficient choice and are exactly the wrong one on these GPUs: after one block only 512 slots remain, and a third of every SM sits empty for the whole kernel.

On an A100, two 1024-thread blocks fit neatly into 2,048 slots. On a 1,536-slot SM, a third of the threads simply never exist. Blocks should be a multiple of 32 (a 100-thread block is really four warps with 28 lanes doing nothing), they shouldn’t be so small that the blocks-per-SM limit caps you first, and “256” is a sane default rather than a law. CUDA even ships cudaOccupancyMaxPotentialBlockSize() to do this arithmetic for you.

Now the important part. Higher occupancy gives the schedulers more warps to choose from, until Little’s law is satisfied. Past that point, extra warps buy nothing, and getting them has a price: capping registers so more warps fit can force spills, and shrinking shared-memory tiles reduces the reuse that moved the kernel right on the roofline. Fast GEMM kernels routinely run at occupancies that look shockingly low, sometimes a single block of 256 threads per SM, because each thread holds dozens of independent accumulations. They satisfy Little’s law through instruction-level parallelism instead.

The right question is never “is occupancy high?”. It’s “is there enough independent work in flight?“

A first look at the profilers

Once you can measure honestly, NVIDIA’s two profilers tell you which wall you’re against, and the trick is knowing which question each one answers.

Nsight Systems shows the whole program as a timeline: CPU calls, kernel launches, copies, and the gaps between them. Its question is where does the time go, and is the GPU ever idle? Surprisingly often the biggest win is right there before you touch a kernel: a stray synchronisation, a copy that could overlap with compute, a thousand tiny launches.

Nsight Compute puts one kernel under a microscope. The hardware can only count a handful of events at once, so it replays the kernel many times, collecting different counters on each pass, flushing the caches and pinning the clocks to base frequency. That makes it the wrong tool for how long and the right tool for why. Its first section, Speed of Light, reports how busy the most-loaded part of the memory system was relative to its peak, and the same for the execution units. Memory high and compute low means memory-bound. Compute high means compute-bound. Both low means the third wall: nothing saturated, everything waiting. Chapter 17 reads the rest of it.

In short: a launch is asynchronous, so check errors and time with events. Size grids with the SM count in mind, and prefer grid-stride loops. Warps execute together, so divergence only costs inside a warp. Every kernel is pinned against memory bandwidth, compute, or latency; the roofline gives the ceiling, Little’s law says how much work must be in flight to reach it, and occupancy is just one way of getting there. And measure honestly: warm up, pick the cache state on purpose, and judge in percent of peak.

Most kernels are memory-bound, so this is where most of the real-world wins live. 6. Global Memory: Coalescing, Sectors and Vectorised Loads

It helps to picture where “global memory” physically is. On a data-centre GPU it isn’t a separate stick of RAM somewhere on the board. It sits right next to the GPU die, on the same package.


The package inside a Tesla P100: the GP100 die in the middle, with its HBM2 memory stacks beside it on the same package. Photo: Fritzchens Fritz via Wikimedia Commons, CC0

Slice that package sideways and the arrangement looks like this:


HBM stacks DRAM dies vertically and places them beside the GPU on a silicon interposer. That short, very wide connection is where HBM’s bandwidth comes from. Diagram: ScotXW via Wikimedia Commons, CC BY-SA 4.0

Even so close, it’s still DRAM: hundreds of cycles away and shared by every SM. So how you ask for it matters enormously, and the first fact to internalise is that global memory doesn’t move the bytes you ask for. The unit of traffic between DRAM, L2 and L1 is a 32-byte sector, and caches organise sectors into 128-byte lines of four sectors each. Ask for one 4-byte float and its whole 32-byte sector comes along, whether you want the other 28 bytes or not.

Now remember that loads are issued per warp. When a warp executes a load, the hardware looks at all 32 addresses together and works out the set of distinct sectors they touch. The traffic for that instruction is the number of distinct sectors times 32 bytes. That’s what coalescing really means: how few sectors a warp’s 32 requests collapse into.


The same 128 useful bytes, delivered three ways. At stride 32 the memory system moves eight times what the warp actually uses.

If thread k reads element base + k, the 32 addresses form one contiguous 128-byte run: exactly 4 sectors, 100% efficiency. That’s what A[blockIdx.x * blockDim.x + threadIdx.x] gives you for free, which is why vector add was already at 91% of peak. At stride 2, the floats spread over 8 sectors, half of each wasted: 50%. At a stride of 32 floats, every thread lands in its own sector: 12.5%, eight times the traffic. Random addresses are the same worst case.

Notice what doesn’t matter on modern GPUs: the order of threads within the warp. If the 32 threads read the 32 floats of one 128-byte block in a scrambled order, it’s still 4 sectors. Very old GPUs demanded perfectly ordered access, and outdated tutorials still repeat that rule. Today it’s purely about how many distinct sectors get touched.

Alignment matters only a little. A 128-byte run that starts 4 bytes past a sector boundary straddles 5 sectors instead of 4, which is 80% efficiency. cudaMalloc hands out memory aligned to at least 256 bytes, so this mostly bites when you offset into an array or use row widths that aren’t multiples of 32 elements. Writes follow exactly the same rules as reads.

Where uncoalesced access comes from

Almost every uncoalesced access in real code comes from one of three places. The first is walking a matrix the wrong way: in a row-major matrix, consecutive elements of a column are a whole row apart, so a warp walking down a column is the stride-equals-width disaster. That’s why threadIdx.x must map to the contiguous dimension.

The second is array of structures:


Same data, same arithmetic. Only the layout changed, and with it a threefold difference in traffic.

Store particles as struct { float x, y, z; } p[N] and have each thread read p[i].x, and consecutive threads’ values are 12 bytes apart, so the warp touches 12 sectors to use 4. Switch to a structure of arrays (separate x[N], y[N], z[N]) and every field read becomes perfectly contiguous.

The third is access that’s inherently scattered: gathers through an index array, transposes, graph neighbours. Some of those can be restructured, for instance by sorting the indices, and some can be routed through shared memory so that the global access is coalesced and the scattering happens on chip (chapter 7).

Vectorised loads

Once access is coalesced, one refinement is left. A warp loading one float per thread issues one instruction per 128 bytes. If each thread loads a float4 with a single 128-bit instruction, the warp moves 512 bytes per instruction: a quarter of the load instructions, a quarter of the address arithmetic, and, by Little’s law, four times the bytes in flight per instruction.

For a streaming kernel sitting at 75 or 80% of peak, this often closes most of the remaining gap. The price is that addresses must be 16-byte aligned, and you need a little cleanup code when the length isn’t a multiple of four.

7. Shared Memory: Tiling, Bank Conflicts, Padding and Swizzling

Coalescing makes every byte you fetch useful. Shared memory makes sure you don’t fetch the same byte twice. It’s a small block of on-chip SRAM on each SM, visible to every thread of a block, with latency in the same class as L1. Unlike a cache, you decide what goes in it and when, and it has two jobs: reuse, and reorganising access patterns. The reuse job is easiest to see side by side:


Without shared memory, every thread goes to DRAM for its own data. With it, a block fetches the data once and its threads reuse it on chip. Diagram: Ricardas.marozas via Wikimedia Commons, CC BY-SA 3.0

Tiling

Matrix multiply is the classic case for reuse. To compute one element of C = A × B, a thread needs a full row of A and a full column of B. Done naively, every thread fetches its own row and column from global memory, and neighbouring threads fetch mostly the same data over and over. For N×N matrices, every element of A and B gets loaded N times. Tiling fixes this by making the threads of a block cooperate.


The block walks along the shared dimension one pair of tiles at a time. Every element it loads gets reused by a whole row or column of threads.

A 32×32 block computes a 32×32 tile of C, walking along the shared dimension in steps of 32. At each step, all 1,024 threads load one 32×32 tile of A and one of B into shared memory, one element each, perfectly coalesced. They synchronise, each does 32 multiply-adds from shared memory, they synchronise again, and the block moves on.

Each element now comes from DRAM once per block instead of once per thread, cutting global traffic by the tile size and moving the kernel rightward on the roofline. The bigger the tile, the more reuse, but shared memory per block is also an occupancy limit, so the tradeoff shows up immediately. Both barriers are essential, and the second is the one people forget: without it, a fast thread can start loading the next tile while a slow one is still reading the current one. That’s a race that produces a wrong answer only occasionally, the worst kind of bug to chase.

The transpose trick

Shared memory’s second job is turning an uncoalesced access into a coalesced one. A matrix transpose has an unavoidable problem: if you read rows coalesced, you must write columns (strided), and vice versa.


The strided access doesn’t disappear. It moves on chip, where it’s cheap. Or almost.

The block reads a 32×32 tile row by row from global memory (coalesced), stores it in shared memory, then reads it back column by column and writes those out as rows of the result (coalesced again). The strided access still happens, but now it happens in shared memory, which brings us to banks.

Bank conflicts

Shared memory isn’t one big memory. It’s split into 32 banks, each 4 bytes wide, with consecutive 32-bit words dealt out to consecutive banks like cards around a table of 32 players:

bank = (byte address ÷ 4) mod 32

Each bank serves one word per cycle. If all 32 threads of a warp hit different banks, everything is served in a single pass. If several threads read the same word, that’s fine too: the value is broadcast. But if two threads hit the same bank at different addresses, the bank serves them one after the other. That’s a bank conflict, and an n-way conflict turns one access into n sequential passes.

Back to the transpose tile, float tile[32][32]. Element tile[r][c] sits at word 32r + c, so its bank is (32r + c) mod 32, which is just c. The row number vanishes. Every element of a column lives in the same bank. Reading a row is perfect; reading a column, which is exactly what the transpose does, sends all 32 threads to one bank, and the read takes 32 passes.

Padding: one extra column

The root cause is a coincidence of numbers: the row length (32 words) is an exact multiple of the bank count (32), so every row starts back at bank 0 and the columns stack up bank on bank. The classic fix is almost embarrassingly small:


Shrunk to 4 banks so you can see it. Without padding, each column is a stack in one bank. With one dead column, every row starts one bank later and columns become a staircase.

Each row is now 33 words long, so tile[r][c] sits at word 33r + c, and its bank is (33r + c) mod 32 = (r + c) mod 32. The row number is back in the formula. Each row starts one bank later than the row above, so walking down a column visits every bank once and the column read takes a single pass. The padding column never holds data; it only pushes the next row along, at a cost of about 3% of the tile.

It also tells you which padding works. With a row length of 34, the bank of tile[r][c] is (2r + c) mod 32, which repeats after 16 rows, so pairs of threads still collide. The row length must share no factor with 32, and since 32 is a power of two, that simply means the row length must be odd.

Swizzling: the same staircase, without the waste

Padding has one real weakness: it breaks alignment. A 33-float row is 132 bytes, so rows no longer start on 16-byte boundaries, which rules out 128-bit vectorised accesses into the tile and clashes with the asynchronous copy hardware and tensor core loads that appear later. So high-performance kernels use swizzling instead.


XOR scrambles each row’s columns differently, so any logical column lands in every bank exactly once. No memory wasted, every row still aligned.

Keep the tile dense, but permute where each element is stored, typically by XORing the column index with bits of the row index: element (r, c) lives at column c ^ r. Reads apply the same XOR and get the right data back. It looks like a hack the first time you see it, but it’s exact, cheap and invertible, which is why CUTLASS and Hopper’s TMA engine have swizzle patterns built in as named hardware modes.

8. Registers: Spilling, Local Memory and Register Blocking

It surprises people the first time: on a modern NVIDIA SM the register file is 256 KB, larger than its shared memory and L1 combined. Registers are the only storage the execution units read directly, with no load instruction at all. Every fast kernel, in the end, is a kernel that keeps its working data in registers.

Registers aren’t shared. Every thread gets its own slice of the register file for its whole lifetime, sized by the peak number the compiler decided the kernel needs. One complicated code path that briefly needs 80 live values makes every thread reserve 80 registers for the entire kernel. And registers are handed out in chunks, so occupancy falls off cliffs:


Going from 32 to 33 registers per thread costs a whole quarter of the SM’s warps, because 33 rounds up to the next allocation unit and one fewer block fits.

With 256-thread blocks on an A100, 32 registers per thread fits 8 blocks, the full 64 warps. Add a single register and the allocation rounds up to 40 per thread; only 6 blocks fit, and occupancy drops from 100% to 75% because of one variable the compiler decided to keep alive a little longer. That’s why the -Xptxas -v report is worth reading on every build.

Spilling, and the misleading name “local memory”

When a kernel needs more registers than it’s allowed (the hardware maximum is 255 per thread, and you can set lower limits), the compiler spills: it parks values in local memory and loads them back when needed. “Local” is one of CUDA’s worst names. Local memory is private to each thread, but it lives in off-chip DRAM, cached in L1 and L2 like any other data. A spill turns a free register access into a memory round trip. A few spills in cold code are harmless; spills in a hot inner loop can make a kernel several times slower.

There’s a second, sneakier way into local memory: arrays indexed with values only known at runtime. Registers can’t be addressed dynamically, so if you write float acc[8]; acc[k] += x; with k decided at runtime, the whole array goes to local memory. If the loop can be fully unrolled so every index becomes a compile-time constant, the array stays in registers. This one detail is behind a surprising number of mysteriously slow kernels.

You can steer the compiler, too. __launch_bounds__(256, 4) tells it “at most 256 threads per block, and aim for at least 4 blocks per SM”, so it caps itself at 64 registers per thread, spilling if it has to. That’s the occupancy tradeoff made concrete: squeeze registers and you get more warps, at the risk of spills. Neither direction is always right, so you try both and measure.

Register blocking

The flip side is that registers are your best tool for reuse, even better than shared memory. In the tiled multiply above, each thread computed one output, reading two values from shared memory per multiply-add. Have each thread compute an 8×8 block of outputs instead, 64 accumulators held in registers, and each value read from shared memory feeds 8 multiply-adds. Shared-memory traffic drops eightfold, and every thread has 64 independent accumulations in flight, exactly the instruction-level parallelism Little’s law asks for. Register blocking is the step that takes a decent matrix multiply to a great one, and it’s why fast GEMMs are happy at low occupancy.

9. The Other Memory Paths

Global memory, shared memory and registers carry almost all of the traffic, but a few specialised paths exist because one access pattern is common enough to deserve its own hardware.

Constant memory is a 64 KB region of read-only data, backed by a small cache on each SM. Its trick is broadcast.


Constant memory is perfect for values that are uniform across a warp, and a trap for anything indexed by threadIdx.

When all 32 threads of a warp read the same address, the value reaches all of them in one access. When they read different addresses, the accesses are serialised, one per distinct address. So it’s ideal for filter coefficients, scaling factors and small tables indexed by something warp-uniform. Your kernel’s arguments live in a constant bank too, which is why passing parameters costs nothing.

The read-only path. Marking a pointer const __restrict__ tells the compiler the data won’t change during the kernel and isn’t aliased by any other pointer, so it can route loads through the read-only side of the L1 cache and reorder them more freely. On modern GPUs that cache is unified with L1, so the gain is smaller than it used to be, but it’s still free performance for one keyword. Texture memory is the graphics heritage of the GPU: hardware interpolation, automatic edge handling, conversion of small integers to floats, and a cache organised for 2D locality. It’s genuinely useful in image processing and rare in ML kernels.

L2 persistence is the newest path and the most relevant to ML.


Tell the hardware which data is worth keeping, and a big stream of one-time reads can no longer push it out.

From Ampere onwards you can set aside part of the L2 for data you know will be reused, and mark a window of memory as persisting (try to keep these lines) or streaming (evict these first). The classic use is a small, hot structure, such as a lookup table or the popular rows of an embedding table, read over and over while a large stream of other data flows past. It’s the cache insertion policies from Ahead of the Pipeline-I, except that this time you decide what’s worth keeping.

In short: global memory moves 32-byte sectors, so what matters is how many distinct sectors each warp touches; keep the fast thread index on the contiguous dimension, prefer structures of arrays, and vectorise. Shared memory turns repeated DRAM reads into on-chip reuse, but its 32 banks punish column access, which padding (odd row length) or swizzling (XOR) fixes. Registers are the biggest and fastest memory on the chip; watch for cliffs and spills, and use them for register blocking. Constant memory broadcasts, and L2 persistence protects hot data.

Part 3: Cooperation

So far threads have mostly worked alone. The moment they need to share partial results, count things or hand data to each other, a new class of problems appears, and parallel code that gets them wrong doesn’t crash: it produces the right answer 999 times and a wrong one on the thousandth. This part covers the rules for cooperating safely, the warp-level tools that make it fast, and the classic patterns built from both.

10. Coordination: Barriers, Atomics and the Memory Model

Three questions come up the moment threads cooperate. When is it safe to read what another thread wrote? How do many threads update one location without trampling each other? And in what order do other threads see my writes?

Barriers

__syncthreads() is a barrier for one block: no thread passes it until every thread of the block has arrived. It does two jobs at once. It synchronises execution, and it guarantees visibility: every write a block’s threads made before the barrier is visible to all of the block’s threads after it. That’s exactly what tiling needed.

It comes with one sharp rule: every thread of the block must reach the same barrier. Put __syncthreads() inside an if that only some threads enter and the behaviour is undefined: the block may hang, or carry on with corrupted shared data.

There’s no barrier across the whole grid inside an ordinary kernel. Blocks run in any order and not all of them are resident at once, so a block waiting for a block that hasn’t been scheduled yet would wait forever (the deadlock from Inside the GPU). The standard grid-wide barrier is the kernel boundary: end the kernel and launch the next one.

Atomics and contention

Suppose many threads each do count += 1 on the same counter. That line is really three steps: read, add, write. Two threads that both read 5 both write 6, and an increment vanishes. An atomic operation performs the read-modify-write as one indivisible step, so atomicAdd(&count, 1) guarantees every increment lands. CUDA provides add, min, max, exchange, the bitwise operations and compare-and-swap, from which any other atomic can be built in a retry loop.

Atomics on global memory are carried out at the L2 cache, and on shared memory by the SM itself, which is far faster. Either way, the cost depends almost entirely on contention. Atomics to different addresses proceed in parallel and are cheap. Atomics to the same address are serialised, so ten thousand threads hammering one counter line up single file.


Privatisation: let each block fight only with its own threads, on the SM, and touch global memory once per bin at the end.

The fixes all reduce contention. Privatisation: in a histogram, each block keeps a private copy in shared memory, updates it with fast shared atomics, and merges it into the global histogram with one atomic per bin per block. Warp aggregation: if all 32 threads of a warp want to add to the same counter, let one leader add the warp’s total (chapter 11 shows how). And hierarchy: reduce within the block first, and touch global memory once.

One side effect matters a lot in ML. Atomic floating-point additions happen in whatever order the threads arrive, and floating-point addition isn’t associative, so the result changes slightly from run to run. That’s why some PyTorch operations are documented as nondeterministic.

Why order isn’t guaranteed

Here’s a pattern that looks obviously correct:

On a GPU it isn’t guaranteed to be. The memory system is weakly ordered: writes from one thread can become visible to other threads in a different order than they were issued.


Both writes are in flight through caches and the memory system. Nothing promises the data arrives before the flag unless you ask.

The fix is a memory fence. A __threadfence() between the two writes guarantees that any thread which sees flag = 1 also sees data = 42. There are narrower and wider versions (__threadfence_block() within a block, __threadfence_system() including the CPU), and the reader must re-read the flag from memory each time, with an atomic or volatile load, rather than spinning on a cached copy.

The modern way to express all this is libcu++: a cuda::atomic with release semantics on the producer’s store (“everything I wrote before this is published along with it”) and acquire semantics on the consumer’s load (“after seeing this, I see everything published with it”). It’s C++’s std::atomic model, extended with scopes (block, device, system), because on a GPU who needs to see a write changes what it costs.

The classic place it all comes together is the single-kernel reduction. Every block writes its partial sum, fences, then atomically increments a counter. The block that sees the counter reach the total knows it finished last and, thanks to the fences, that every partial sum is visible. So it adds them up: a grid-wide reduction with no second kernel and no grid barrier.

11. Warp-Level Programming: Shuffles, Votes and Cooperative Groups

The 32 threads of a warp sit side by side in hardware. Making them communicate through shared memory (write, barrier, read) is like two people at the same desk exchanging notes by post. Warp-level primitives let lanes read each other’s registers directly, in one instruction, with no shared memory and no block-wide barrier.

Shuffles

__shfl_sync(mask, value, srcLane) lets every lane read value from another lane’s registers. Its variants express the common patterns: __shfl_down_sync reads from the lane d positions higher, __shfl_up_sync from d lower, and __shfl_xor_sync from the lane whose id is yours XOR m. The canonical use is summing 32 values, one per lane:


Each step folds the warp in half. Because the pattern is a butterfly, every lane ends up with the full sum, not just lane 0.

Five steps for 32 values. XOR is the elegant choice because the pattern is symmetric, so every lane ends with the complete sum, handy whenever everyone needs the result. A softmax, for instance, needs the row maximum in every lane.

Votes and matches

Votes answer questions about the whole warp in one instruction. __ballot_sync(mask, predicate) hands every lane a 32-bit integer whose bit i says whether lane i’s predicate was true, and that bitmask is surprisingly powerful.


A whole stream compaction for one warp: one ballot, one popcount, and each survivor knows exactly where to write.

__popc(ballot) counts the lanes that said yes. __popc(ballot & ((1u << lane) - 1)) counts the yes-lanes below you, which is exactly the slot you should write to when packing the survivors of a filter together. Picking the lowest set bit as a leader gives you warp-aggregated atomics: one atomicAdd of the popcount per warp instead of 32. And __match_any_sync tells each lane which other lanes hold the same key, so lanes heading for the same histogram bin can elect one leader per bin.

Every one of these takes a mask naming the participating lanes, most often 0xffffffff. That’s the price of independent thread scheduling: the hardware no longer assumes lanes are in lockstep, so you must say which ones you expect to be together, and every lane named must reach that same instruction.

12. The Classic Parallel Patterns

Real kernels rarely invent a new kind of parallelism. They’re assembled from a handful of patterns, and each one is a compact lesson in everything above.

Reduction

Reduction (summing or taking the maximum of a large array) is a tree: pairs combine, then pairs of pairs, halving each round. Mark Harris’s classic NVIDIA write-up optimises it in seven steps, and the order of the steps is a tour of this post so far.


Same tree, same number of additions. Packing the active threads at the front means whole warps finish early instead of every warp running half empty.

The first version halves the active threads with if (tid % (2*s) == 0), which scatters them across every warp, so nearly every warp diverges. Re-indexing so the active threads are the first half of the block keeps whole warps either busy or idle, and the sequential addressing that comes with it also removes the bank conflicts. The biggest win comes next: have each thread sum many elements serially with a grid-stride loop before the tree starts, so the synchronised tree only handles one value per thread and the kernel becomes a pure streaming read. Then finish the last 32 values inside one warp with shuffles.

On the 2007-era GeForce 8800 GTX his slides used, those steps took the kernel from about 2 GB/s to about 63 GB/s, roughly 30 times faster and close to three quarters of that card’s peak bandwidth. A good reduction is purely memory-bound, so that’s exactly how it should be judged.

Scan

Scan, or prefix sum, replaces each element with the sum of everything before it: [3, 1, 4, 1] becomes [3, 4, 8, 9]. It looks inherently sequential, and that’s precisely why it matters: scan is how threads find out where to write when the size of the output depends on the data.


Three steps for eight elements. Simple, but it does more total work than it needs to.

The simple Hillis-Steele version does log n rounds in which every element adds the value 2ᵏ places to its left, but it does O(n log n) work. Blelloch’s work-efficient version does O(n) work in two sweeps over a tree. For arrays bigger than a block, the textbook approach scans each block, scans the block totals, and adds the offsets back, reading the data more than once. The state of the art is Merrill and Garland’s single-pass scan with decoupled look-back, where each block publishes its total as soon as it knows it and the next block looks back at its predecessors’ published values instead of waiting. It runs at roughly the speed of a plain memory copy, and it’s what NVIDIA’s CUB library uses.

Histogram, compaction, stencil, transpose and sort

Histogram is the textbook atomic workload, and its speed depends on the data: evenly spread values rarely collide, while skewed data hammers a few bins. Privatised shared-memory histograms are the standard answer. Stream compaction keeps only the elements that pass a test, packed together: flag each element, exclusive-scan the flags to find each survivor’s output slot, scatter. It shows up in more places than you’d expect, including the top-p filter at the end of every LLM sampling step.

Stencils (each output depends on a neighbourhood: blurs, finite differences) load a tile plus a halo into shared memory so neighbours are read on chip. The transpose from chapter 7 is worth remembering as a benchmark in its own right, since a well-written one runs at nearly copy speed. Sorting on GPUs is mostly radix sort, built entirely from histograms and scans, and in practice you call CUB or Thrust rather than writing it.

Sparse matrices and uneven work

The last pattern teaches the hardest lesson: uneven work. In a sparse matrix stored row by row (the CSR format), rows can have two non-zeros or twenty thousand.


Balance the work itself, not the rows it happens to be grouped into.

One thread per row is the worst of everything: long rows hold whole warps hostage, and each thread walks its own row, so neighbouring threads read far-apart memory. One warp per row fixes the coalescing but wastes lanes on short rows. Merge-path load balancing is the real answer: divide the total work into exactly equal chunks, one per thread, regardless of where the row boundaries fall. It’s the general cure for irregular work, and the same idea comes back as Stream-K in chapter 20.

In short: barriers order a block, atomics make read-modify-write safe but serialise on contention (privatise, aggregate, reduce hierarchically), and GPU memory is weakly ordered, so publishing data to other blocks needs fences or release/acquire. Inside a warp, shuffles, ballots and matches replace shared memory, and cooperative groups make the scope explicit. The patterns (reduction, scan, histogram, compaction, stencil, sort, sparse) are built from these pieces, and uneven work is fixed by balancing the work itself.

Part 4: Arithmetic

Once the bytes arrive on time, the bottleneck moves to the maths itself. This part covers the instruction level (which instructions cost what, how many bits you really need, and how to keep results trustworthy), the tensor cores that changed what a GPU is for, the road from a naive matrix multiply to cuBLAS, and the asynchronous pipelines that keep tensor cores fed.

13. Instruction-Level Optimisation, Precision and Numerics

Not all instructions are equal

An SM has several execution pipes, each with its own throughput. On recent NVIDIA SMs the FP32 pipe completes 64 or 128 fused multiply-adds per cycle, depending on the generation. The special function unit, which handles sin, cos, exp, log, reciprocals and square roots, completes only around 16 per cycle, between a quarter and an eighth of the FMA rate. Double precision varies enormously: data-centre GPUs run FP64 at half the FP32 rate, consumer GPUs at a sixty-fourth.

Some innocent-looking operations aren’t single instructions at all. Integer division and modulo by a runtime value compile into dozens of instructions, so a hot loop computing i % width can spend more time on that one operator than on its actual work. Use shifts and masks when the divisor is a power of two, precompute reciprocals and multiply, and hoist anything that doesn’t change out of the loop.

Instruction-level parallelism

Every instruction also has a latency, a few cycles for an FMA and more for the special functions. A thread doing acc += a[i] * b[i] builds a dependency chain in which each FMA waits for the previous one, capping every warp’s speed however many warps exist.


Same instructions, same latency. Splitting one chain into four lets the scheduler issue something every cycle.

The fix is Little’s law again, applied to arithmetic: give each thread several independent accumulators, four chains instead of one, combined at the end, and let #pragma unroll turn small loops into straight-line code the scheduler can interleave. Register blocking in matrix multiply is this idea taken to its limit.

Fast-math intrinsics

CUDA offers fast, approximate versions of the expensive functions: __expf, __logf, __sinf, __fdividef and friends. They map almost directly onto the special function hardware and run several times faster than the accurate versions, at the cost of a few units in the last place, and much worse accuracy for very large or awkward inputs. The flag --use_fast_math switches all of them on at once, and also flushes tiny denormal numbers to zero and approximates division and square root.

That’s a fine trade inside a softmax or an activation function, where a small relative error disappears into the noise. It’s a dangerous one in a solver, where small errors accumulate. Use the intrinsics deliberately, in the hot spots that tolerate them, rather than flipping the global switch and hoping.

How many bits do you need?

Every floating-point format splits its bits between an exponent, which sets the range, and a mantissa, which sets the precision.


Exponent bits buy range, mantissa bits buy precision. Every format is a different bet on which one matters more.

FP16 has reasonable precision but a tiny range: anything above 65,504 becomes infinity. Activations and gradients regularly go past that, which is why FP16 training needed loss scaling. BF16 keeps FP32’s 8 exponent bits, so it has the same range and no overflow surprises, and pays with only 7 mantissa bits; training turned out to care much more about range than precision, and BF16 became the default. TF32 is what tensor cores use when you hand them FP32 data: FP32’s range with FP16’s precision. FP8 goes further in two variants that split the bits differently, and only works with careful scaling into the narrow window it can represent.

Two rules hold across all of them. First, accumulate in higher precision: multiply in FP16 or FP8 if you like, but add the products up in FP32, because a long low-precision sum silently drops small contributions once the total gets large. Second, low precision helps memory-bound kernels too: FP16 data is half the bytes of FP32, so an elementwise kernel gets up to twice as fast from the smaller type alone.

Numerics and determinism

Because (a + b) + c and a + (b + c) can differ in the last bits, a parallel reduction gives a slightly different answer from a serial loop, and with atomics the answer changes between runs. None of this is a bug, but it means testing must compare with tolerances, an absolute tolerance plus a relative one chosen for the precision, never exact equality. When a long sum loses too much accuracy, Kahan summation carries a running compensation term that recovers most of it. And when bit-for-bit reproducibility matters, you pick deterministic algorithms that fix the order of operations and accept some loss of speed.

14. Tensor Cores and the Road to a Fast GEMM

Everything so far has been about feeding scalar FMA units. Tensor cores change the unit of work. A single tensor core instruction computes a small matrix multiply-accumulate, D = A × B + C, on tiles like 16×8×16, inside the hardware, in one go. An A100 does 19.5 TFLOP/s of plain FP32 maths but 312 TFLOP/s of dense FP16 matrix maths on its tensor cores, sixteen times more. Any kernel that can be expressed as matrix multiplication and doesn’t use tensor cores is leaving most of the chip idle.

WMMA and mma.sync

The friendly way in is the WMMA API, where a whole warp cooperatively holds tiles called fragments:

A WMMA fragment is opaque: its elements are spread across the warp’s registers in a layout the API deliberately hides. That keeps things simple, but you can’t easily touch specific elements. So production kernels go one level down, to the PTX instruction mma.sync, where the layout is documented exactly.


The documented layout of one mma.sync accumulator. Knowing which lane holds which value is what lets a kernel fuse work onto the results in registers.

Knowing the layout lets you fuse work directly onto the accumulators (scale them, add a bias, apply an activation) before anything touches memory. Its companion, ldmatrix, loads small sub-tiles from shared memory straight into that register layout in one instruction, and its access pattern is precisely why tensor core tiles in shared memory are swizzled rather than padded.

The GEMM ladder

The best way to see how a matrix multiply gets fast is as a ladder, where each rung removes the bottleneck the previous one exposed. Simon Boehm’s well-known FP32 walkthrough on an RTX A6000 gives real numbers for every rung:


From 1.3% to 93.7% of cuBLAS. Every rung is an idea from earlier in this post.

Read it as a story. Fixing coalescing (chapter 6) is worth six times, because the naive kernel wasted most of every sector it touched. Shared-memory tiling (chapter 7) adds less than you’d expect, because the bottleneck simply moves to shared-memory bandwidth and instruction overhead. Register blocking (chapter 8) is the big jump: each value read from shared memory now feeds many FMAs, and every thread has plenty of independent work. Vectorised loads and tuned tile sizes trim the remaining overhead, and warp tiling, which organises the work so each warp computes its own sub-tile, closes most of the remaining gap. All of that is on plain FP32 cores; moving the inner loop onto tensor cores and hiding load latency with asynchronous copies (chapter 15) is how cuBLAS reaches the far higher half-precision numbers.

2:4 structured sparsity

My compression post ended on a frustrating note: unstructured sparsity doesn’t speed anything up, because the hardware can’t exploit zeros in random positions. 2:4 structured sparsity is the hardware’s answer.


Exactly two of every four weights are zero, so the hardware knows where to skip. The metadata says which two survived.

From Ampere onwards, tensor cores natively skip two zeros out of every four weights, with a little metadata recording which two survived. Prune a model to exactly that pattern, usually with some fine-tuning to recover accuracy, and the maths runs up to twice as fast.

15. Asynchronous Copies and Software Pipelining

Even with perfect tiling, the tiled matrix multiply has a rhythm with a hole in it: load a tile, synchronise, compute, synchronise, repeat. While the tile loads, the tensor cores sit idle; while they compute, the memory system sits idle. A fast GEMM uses so much shared memory and so many registers that only a few warps fit per SM, so there’s nobody else to switch to. The fix is to make one block overlap its own loading and computing.

Ampere introduced cp.async, an instruction that copies data from global memory directly into shared memory, without passing through registers and without blocking the thread that issued it. Copies are grouped into commit groups, and the thread waits on a specific group only when it actually needs that data.


Same four tiles. Once the copies run ahead of the maths, the tensor cores never wait for memory.

This is software pipelining. Shared memory holds a small ring buffer of tiles, the stages, and at any moment one stage is being computed on while the next ones are already on their way:

With two stages it’s classic double buffering; production kernels typically use three to five. More stages tolerate more memory latency (Little’s law, once again), but each stage costs a whole tile of shared memory, which can push occupancy down, so the stage count is usually a tuned parameter. There’s a bonus too: data no longer passes through registers on its way to shared memory, so register pressure drops, freeing registers for bigger accumulator tiles. In machine code it shows up as LDGSTS, “load global, store shared”.

In short: instructions have very different costs, and dependency chains need independent accumulators to keep the pipes full. Use fast-math intrinsics deliberately, choose the narrowest format that keeps enough range, always accumulate in FP32, and test with tolerances. Tensor cores multiply matrices, not numbers, and knowing their register layout enables fused epilogues. The GEMM ladder is the whole post in miniature, and asynchronous copies with multistage pipelines are what keep tensor cores from waiting on memory.

Part 5: Beyond One Kernel

A fast kernel inside a slow program is still a slow program. This part steps outside the single kernel: how work overlaps, how launch overhead disappears, how memory is managed and shared across GPUs, how to find out what’s really going on with the profiler and the debugging tools, and which libraries to reach for before writing anything yourself.

16. The System Level: Streams, Graphs, Memory and Many GPUs

Streams and overlap

A stream is a queue of GPU work that executes in order, and work in different streams can run at the same time. By default everything goes into one stream, so a copy to the GPU, a kernel and a copy back run strictly one after another. But GPUs have separate copy engines that move data over PCIe while the SMs compute. Here’s the round trip every CUDA introduction starts with:


The classic CUDA round trip: copy in, launch, run in parallel, copy out. In a single stream, each step waits for the one before it. Diagram: Tosaka via Wikimedia Commons, CC BY 3.0


The kernel didn’t get any faster. The copies just stopped waiting for each other.

Split a big job into chunks spread across several streams and chunk 2’s upload overlaps chunk 1’s compute and chunk 0’s download. Two details are easy to miss. Asynchronous copies only truly overlap if the host memory is pinned (cudaMallocHost), because the copy engine needs memory the operating system promises not to move. And the old default stream implicitly synchronises with every other stream, quietly destroying the overlap, unless you use per-thread default streams or create explicit ones. Events, besides timing, let one stream wait for a point in another (cudaStreamWaitEvent), which is how dependencies between streams are built without stalling the CPU.

CUDA Graphs and launch overhead

Remember that launches cost a few microseconds each. For a model whose forward pass is hundreds of small kernels, as in LLM decoding, the CPU can’t launch them as fast as the GPU finishes them, and the GPU sits idle in the gaps.


Record the sequence once, replay it with one launch. The GPU stops waiting for the CPU.

CUDA Graphs fix this by recording a whole sequence of operations once (capturing a stream as it runs) and replaying it as a single launch with every dependency already resolved. The catch is that a graph is frozen: same kernels, same shapes, same memory addresses. That’s why inference engines like vLLM capture a separate graph for each of a set of batch sizes and pick the right one every step.

On Hopper, programmatic dependent launch attacks the gap from inside the GPU. Normally kernel B can’t start until kernel A has completely finished; with PDL, B can launch early and run its setup (loading weights that don’t depend on A, say) while A is wrapping up, then wait at an explicit point only for the part that needs A’s results.

Memory management

Unified memory (cudaMallocManaged) gives one pointer that’s valid on both CPU and GPU, with pages migrating automatically when touched. It’s convenient, but page faults are slow, so performance code adds explicit prefetches or avoids it. Zero-copy memory maps pinned host memory into the GPU’s address space so a kernel reads it directly over PCIe, fine for data touched exactly once.

The stream-ordered allocator (cudaMallocAsync, cudaFreeAsync) allocates from a pool in stream order, which matters because a plain cudaFree synchronises the whole device, a hidden stall inside loops. And virtual memory management separates reserving an address range from backing it with physical memory, so a buffer can grow in place without being copied. PyTorch’s “expandable segments” allocator option is built on exactly that.

Many GPUs

With more than one GPU, devices can read each other’s memory directly (peer-to-peer) over NVLink at hundreds of GB/s, or more slowly over PCIe. In a data-centre server, that usually means eight GPUs on one baseboard:


The HGX module from a DGX B200: eight Blackwell GPUs on one baseboard, wired together by NVLink so collectives between them never touch PCIe. Photo: Pokiiri via Wikimedia Commons, CC BY-SA 4.0

NCCL provides the collective operations that distributed training and multi-GPU inference live on.


In a ring all-reduce every link stays busy and each GPU sends about twice its buffer in total, however many GPUs join.

Its ring and tree algorithms are tuned to the actual wiring between GPUs. GPUDirect RDMA lets a network card read and write GPU memory without involving the CPU, which is what makes multi-node training practical, and NVSHMEM lets kernels themselves put and get data in other GPUs’ memory, mid-kernel.

Kernels that schedule themselves

Dynamic parallelism lets a kernel launch other kernels; it sounds powerful but is rarely the best tool, since device-side launches aren’t free. Cooperative kernels get a real grid-wide barrier, on the condition that the whole grid fits on the GPU at once. And persistent kernels turn the usual model inside out.


One block per SM, looping until the work runs out. No relaunches, no tail.

A persistent kernel launches exactly as many blocks as fit on the GPU, then each block loops, pulling work items from a queue until there’s none left. That removes per-tile launch costs and wave quantization, and lets a block overlap the end of one tile with the loads for the next. Most state-of-the-art matrix multiply and attention kernels on Hopper are persistent.

Sharing one GPU

MPS lets kernels from several processes run on one GPU at the same time instead of taking turns, which helps when no single process can fill it. MIG, on A100 and H100, goes the other way and splits one GPU into as many as seven fully isolated slices, each with its own SMs, memory and bandwidth.

17. Profiling and Debugging in Depth

Chapter 5 used the profilers to find which wall a kernel was against. With the memory system and the patterns behind us, the rest of Nsight Compute starts making sense.

For a memory-bound kernel, the memory workload analysis shows traffic at every level (L1, L2 and DRAM throughput, hit rates) and, most usefully, sectors per request. For 4-byte loads, 4 sectors per request means perfect coalescing and 32 means every lane is touching its own sector; that single number exposes most access-pattern bugs. The same section reports shared-memory bank conflicts directly.

For a latency-bound kernel, the scheduler statistics say how many warps were eligible to issue in an average cycle. If that’s often zero, the issue slot went to waste. The warp state statistics then say why warps weren’t ready:


The stall reasons are a precise vocabulary. Each one points at a specific wall, and usually at a specific fix.

With -lineinfo, the source view pins all of this onto your own lines, next to the machine code the compiler actually generated.

Reading SASS

You don’t need to write SASS, but reading a little of it confirms whether the compiler did what you assumed. LDG and STG are global loads and stores (LDG.E.128 means your float4 really did become one 128-bit load). LDS and STS are shared memory. LDL and STL are local memory, which means spills, a red flag in a hot loop. FFMA is an FP32 fused multiply-add, HMMA a tensor core instruction, LDGSTS an asynchronous copy, BAR.SYNC a barrier, SHFL a shuffle, and an @P0 prefix marks predicated execution. cuobjdump -sass or the source view shows it all.

Bugs that don’t announce themselves

compute-sanitizer runs your program under instrumentation with four tools. memcheck catches out-of-bounds and misaligned accesses and reports the exact thread, block and line, which is how the silent overrun from chapter 1 gets caught. racecheck finds shared-memory hazards, two threads touching the same location with no barrier between them: the missing second __syncthreads() from chapter 7. initcheck reports reads of memory that was never written, and synccheck catches barriers used illegally, such as inside divergent code. It makes the program much slower, but it turns silent corruption into a precise report.

cuda-gdb is a real debugger for device code, with breakpoints inside kernels and the ability to switch to any block and thread and inspect its variables. And the simplest trick of all: setting CUDA_LAUNCH_BLOCKING=1 makes every launch synchronous, so an asynchronous error gets reported at the kernel that actually caused it.

18. Libraries and Abstractions

Knowing how to write a kernel is what tells you when not to. Most production GPU code calls libraries, and the skill is knowing what each layer offers.


Start at the top and drop down a layer only when the one above can’t do what you need.

cuBLAS is dense linear algebra: matrix multiplies in every precision, batched versions for many small problems, and cuBLASLt, the flexible interface with FP8 support and epilogue fusion, which applies a bias and a ReLU or GELU inside the GEMM so the result doesn’t take an extra trip through memory. cuDNN covers convolutions, normalisation and fused attention. CUB provides the patterns from chapter 12 at warp, block and device level, and Thrust wraps similar functionality in an STL-like interface. libcu++ brings C++ standard-library facilities to device code, including the scoped cuda::atomic from chapter 10. You hand-write a kernel when the library can’t do what you need: fusing operations so data stays on chip, unusual shapes or new data types, or a whole operation like attention that no single library call expresses efficiently.

CUTLASS and CuTe

Between the libraries and raw CUDA sits CUTLASS, a template library that exposes the structure of a high-performance GEMM so you can customise it: the block, warp and instruction tile hierarchy, swappable pipeline schedules, and custom epilogues. Underneath CUTLASS 3 and later is CuTe, a genuinely different idea: a layout algebra. A layout is a shape and a stride, (4,8):(1,4) for example, read as a function from coordinates to memory offsets. Composition, tiling and partitioning then let you express “split this tile among these threads in this pattern, then among these registers” as algebra rather than hand-written index arithmetic, and the same code adapts to a different tile size or hardware generation. It’s how NVIDIA writes its own Hopper and Blackwell kernels, and CUTLASS 4 exposes it from Python through the CuTe DSL.

Tile languages and inline PTX

Higher still, Triton lets you write kernels in Python at the level of blocks of data: you say “load this tile, multiply these tiles”, and its compiler handles coalescing, shared-memory staging, swizzling and pipelining. It’s what torch.compile generates, and it gets close to hand-written performance for a large class of kernels. Gluon is its lower-level sibling for experts who need control over layouts and warp specialisation, and NVIDIA’s own CUDA Tile model (cuTile in Python, introduced with CUDA 13.1) moves the official stack toward the same tile-based style.

At the very bottom, when you need an instruction no API exposes yet, you can drop into inline PTX with asm volatile(...). It’s precise and occasionally essential, but the compiler loses its understanding of what that code does and mistakes stay silent, so wrap the one instruction you need in a small, well-tested helper and leave it there.

In short: streams and pinned memory overlap copies with compute, and CUDA Graphs remove launch gaps for sequences of small kernels. Prefer stream-ordered allocation, use NCCL for collectives, and consider persistent kernels when tiles are heavy. In Nsight Compute, sectors per request and warp stall reasons point straight at the fix, SASS confirms what the compiler did, and compute-sanitizer catches the bugs that don’t crash. Reach for cuBLAS, cuDNN and CUB first, CUTLASS when you need a custom GEMM, Triton for fast fused kernels, and raw CUDA or PTX only when nothing above will do.

Part 6: ML Kernels and New Hardware

This is where everything comes together. The kernels that run large language models are made of the same ideas as everything above (memory-bound reductions, fused elementwise work, tensor core GEMMs, pipelining), and the newest GPUs are designed around them. This part walks through the small kernels, the decode-time GEMV problem, quantised kernels, FlashAttention, getting a kernel into PyTorch, and finally Hopper and Blackwell.

19. The Small Kernels LLMs Depend On

Around every big matrix multiply in a transformer sit a handful of small kernels. They’re all memory-bound, so making them fast means touching memory once and fusing work together.

Softmax, online

Softmax over a row needs the maximum (for numerical stability), then the sum of exponentials, then a final normalisation: three passes over the data, done naively. Online softmax (Milakov and Gimelshein, 2018) does it in one.


Keep a running max and a running sum; whenever the max grows, rescale the sum so far. One pass, exactly the same answer.

Keep a running maximum and a running sum, and whenever a new element raises the maximum, rescale the sum so far by exp(old_max − new_max). A warp handles a short row with the shuffle reduction from chapter 11; a block handles a long one. Keep that rescaling trick in mind, because it’s the heart of FlashAttention.

Norms, rotary embeddings and sampling

LayerNorm and RMSNorm reduce a row to its mean and variance and then rescale every element. Welford’s algorithm computes both in one numerically stable pass, and production kernels fuse the norm with the residual addition before it, so the row is read once and written once. Rotary position embeddings rotate pairs of elements of the query and key vectors by position-dependent angles; they’re purely elementwise, so they’re usually fused into whatever kernel produces Q and K. And sampling turns logits into the next token: temperature scaling, then top-k (a selection problem) and top-p, which is a sort, a prefix sum over the probabilities and a cut: the stream compaction from chapter 12.

20. GEMV, Split-K, Stream-K and Grouped GEMM

When a model generates one token at a time for a single user, every weight matrix multiplies a single vector. That’s a GEMV, not a GEMM.


Every weight is read once and used for one multiply-add. The kernel runs at exactly the speed of reading the weights.

Each weight is used for a single multiply-add, so the kernel sits at the far left of the roofline and runs at exactly the speed of reading the weights from memory. Tensor cores barely help. A good GEMV puts a warp (or a few) on each output row, uses wide vectorised loads, and finishes with a shuffle reduction. Since the bytes of the weights are the bottleneck, shrinking the weights speeds up decoding almost directly, which is the entire reason weight quantisation matters so much for inference.

Batch a few requests together and the shapes become small, skinny GEMMs, with a new problem: when M and N are small but K is huge, there aren’t enough output tiles to keep every SM busy. Split-K divides the long K dimension across several blocks, each computing a partial sum, and adds the partials at the end.


Share out the work, not the tiles. Tiles that end up split across SMs are finished by adding their partial sums.

Stream-K is the general cure for the wave quantization from chapter 2. Instead of handing whole tiles to blocks, it divides the total multiply-accumulate work evenly across exactly as many blocks as there are SMs, even if some tiles end up split between two of them. Grouped GEMM handles mixture-of-experts models, which run many small multiplies of different sizes, one per expert, by launching them all as one kernel that walks a list of problems.

21. Quantised Kernels: FP8, FP4 and INT4

Weight-only quantisation stores weights in INT4 (as in AWQ or GPTQ) while activations stay in FP16, and the trick is to dequantise inside the kernel.


Read a quarter of the bytes, expand in registers, feed the tensor cores. The full-width weights only ever exist on chip.

Load packed 4-bit weights, a quarter of the bytes, unpack and scale them to FP16 in registers, and feed them straight to the tensor cores, never writing anything back at full width. Kernels like Marlin do this so efficiently that, for batch sizes up to about 16 to 32, they get close to the ideal 4× speedup that reading a quarter of the bytes promises.

FP8 quantises both weights and activations, with scaling factors per tensor, per channel or per block to keep values inside the format’s narrow range, and the tensor cores multiply FP8 directly while accumulating at higher precision. Blackwell pushes the same idea to FP6 and FP4 with hardware block scaling, which chapter 25 comes back to.

22. FlashAttention

Standard attention computes softmax(QKᵀ)V. The intermediate QKᵀ is an N×N matrix for a sequence of length N, so for long sequences it’s enormous, and writing it to memory and reading it back dominates the runtime. On the roofline, attention computed this way is memory-bound for no good reason. The maths isn’t the problem; the round trip is.

FlashAttention never materialises that matrix. It tiles Q, K and V through shared memory, keeping one block of queries on chip while streaming tiles of K and V past it, and computes the softmax online: for each query row it keeps a running maximum and sum, and whenever a new tile raises the maximum, it rescales the partial output accumulated so far. That’s chapter 19’s trick, applied to a whole attention block.


The N×N scores only ever exist one tile at a time, on chip. What’s left is reading Q, K and V once and writing O once.

The result is exact attention with far less memory traffic. The original paper (Dao and colleagues, 2022) reported up to a 3× speedup on GPT-2 training at sequence length 1K. FlashAttention-2 reorganised the work so more of it happens in fast matrix instructions and parallelised across the sequence, reaching 50 to 73% of an A100’s theoretical peak. FlashAttention-3 was rebuilt around Hopper’s new hardware and reached up to about 740 TFLOP/s in FP16 on an H100, roughly 75% of peak, and close to 1.2 PFLOP/s in FP8. It’s this whole post in one kernel: tiling, an online reduction, shared memory, tensor cores, pipelining, and on Hopper, everything in chapter 24.

24. Hopper: Moving Orchestration Into Hardware

Hopper (the H100) rebuilt the data-movement side of the SM, and the theme is simple: stop spending threads on bookkeeping. Everything in this chapter lives inside the chip on these cards:


H100 cards. Everything in this chapter (TMA, mbarrier, clusters, wgmma) lives inside the GH100 chip under those shrouds. Photo: 极客湾Geekerwan via Wikimedia Commons, CC BY 3.0

The Tensor Memory Accelerator (TMA) is a hardware copy engine. You describe a tensor once in a descriptor (its shape, strides, the tile size and a swizzle mode), and then a single thread issues a bulk copy of a whole tile into shared memory. Every other thread is free, and the swizzle from chapter 7 is applied for you. Knowing when such a copy has landed needs a new kind of barrier, the mbarrier, which lives in shared memory and counts bytes: a consumer declares how many bytes it expects, and the barrier completes when the TMA has delivered them.


Blocks in a cluster are guaranteed to run at the same time on neighbouring SMs, can reach each other’s shared memory, and can share a single multicast load.

Thread block clusters group several blocks that are guaranteed to run at the same time on neighbouring SMs, and blocks in a cluster can read and write each other’s shared memory directly (distributed shared memory); TMA can even multicast one tile to every block in a cluster at once. And wgmma, warpgroup MMA, lets four warps (128 threads) issue one larger, asynchronous tensor core operation that reads its operands directly from shared memory, so tiles get bigger, register pressure drops, and threads keep working while the maths runs.

Warp specialisation

The pattern that ties all of this together is warp specialisation.


Producers only move data, consumers only do maths, and barriers in shared memory keep them in step.

Instead of every warp doing everything, producer warps only issue TMA loads into a ring of pipeline stages, and consumer warpgroups only wait for full stages, run wgmma, and hand the empty slots back. Producers need almost no registers, so setmaxnreg moves registers from them to the consumers’ accumulators. Schedules like ping-pong alternate two consumer warpgroups so one writes out its results while the other runs matrix maths. This is the shape of FlashAttention-3 and of CUTLASS’s Hopper kernels, usually wrapped in a persistent kernel that keeps every SM busy from start to finish.

25. Blackwell: The Accumulators Leave the Register File

Data-centre Blackwell (the B200 generation) continues in the same direction. In its densest form, it looks like this:


GB200 at Computex 2024: each superchip pairs a Grace CPU with two Blackwell GPUs, packed so densely that they’re liquid-cooled. Photo: 极客湾Geekerwan via Wikimedia Commons, CC BY 3.0

What’s new is inside each of those GPUs:


Blackwell frees the register file almost entirely, and lets two SMs share the operands of one large multiply.

Its new tensor core instruction, tcgen05.mma, is issued by a single thread on behalf of the whole block, and the accumulators no longer live in the register file at all. They live in a new on-chip Tensor Memory, 256 KB per SM. CTA pairs let two blocks on neighbouring SMs cooperate on one larger matrix multiply, sharing operands so each SM loads only half of them. And the tensor cores natively understand block-scaled formats (MXFP8, MXFP6, MXFP4 and NVIDIA’s NVFP4), where every small block of 16 or 32 values carries its own scale factor, so even 4-bit numbers keep useful precision. One caveat: consumer Blackwell GPUs don’t have tcgen05 or Tensor Memory; they extend the older mma.sync style with the new low-precision formats.

Almost every chapter of this post maps onto one of these boxes.

Step back and the direction across generations is unmistakable. Each one moves more of the orchestration (data movement, synchronisation, accumulation) out of ordinary threads and into dedicated hardware, and asks the programmer to think in tiles and pipelines rather than individual threads. That’s exactly why tile-based languages like Triton, CuTe and cuTile are where GPU programming is heading.

In short: the small LLM kernels are memory-bound, so fuse them and read each row once; online softmax makes softmax a single pass. Decode is a GEMV that runs at the speed of reading the weights, which is why quantisation pays off almost directly, and Split-K, Stream-K and grouped GEMM handle the awkward shapes. FlashAttention never writes the N×N scores, and that’s the whole trick. Hopper moves copies and synchronisation into hardware (TMA, mbarrier, clusters, wgmma, warp specialisation), and Blackwell moves the accumulators out of the register file.

Putting It Together

For all the ground this covered, the method underneath it is small enough to fit in one picture.


Every chapter in this post is an answer to one of these three branches.

Measure honestly: warm up, use events, choose the cache state on purpose, take the median. Turn the time into a percentage of peak, because that’s what tells you how much room is left. Find the wall. If it’s memory, the only cure is moving fewer bytes: coalescing, shared-memory reuse, register blocking, fusion, smaller types (Part 2). If it’s compute, make the maths cheaper: tensor cores, lower precision, fewer operations (Part 4). If it’s neither, go back to Little’s law and find more independent work in flight, through more warps or more instruction-level parallelism, then reach for pipelines and asynchronous copies so the work keeps flowing. And put the kernel on the roofline to see how far it still is from the ceiling its intensity allows.

None of it involves guessing, which is the whole point.

Why I Find This So Satisfying

What I like most about all of this is how much of a modern GPU one formula from 1961 explains. Once you’ve done the Little’s law arithmetic, the architecture stops looking arbitrary. Why does an SM keep dozens of warps resident instead of a handful? Because the architects did the same multiplication: bandwidth times latency, divided by what one warp can request. Why is the register file bigger than shared memory and L1 put together? Because keeping all those warps resident, with free switching between them, means holding every one of their registers at once. Why does every new generation add asynchronous copy engines, byte-counting barriers and deeper pipelines? Because latency barely improves while bandwidth and compute keep growing, so the amount of work that has to be in flight keeps going up.

The GPU is basically Little’s law cast in silicon, and Hopper and Blackwell are what happens when the hardware starts doing the bookkeeping itself.

And it ties straight back to the Tradeoffs post: know what you’re optimising for. A kernel at 91% of peak bandwidth doesn’t need more arithmetic tricks. A kernel at 30% with both units idle doesn’t need a better access pattern. Knowing which wall you’re against is worth more than any single trick in this post.

Coalescing explains why shared memory matters, shared memory explains bank conflicts, Little’s law explains occupancy and pipelining, and FlashAttention is just all of them at once.
