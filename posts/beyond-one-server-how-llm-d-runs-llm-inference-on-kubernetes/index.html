Beyond One Server: How llm-d Runs LLM Inference on Kubernetes

2026-10-10

Kubernetes thinks every pod is the same. An LLM fleet is anything but.


Cover photo: PiDatacenters via Wikimedia Commons, CC BY-SA 4.0

In my last post, Tokens at Scale-I, I followed a request through a single serving engine: prefill and decode, the KV cache, continuous batching, PagedAttention, and how vLLM squeezes thousands of users onto one GPU. Near the end, in the routing section, I mentioned llm-d in a single line, as one of the routers that knows which replica holds which cache. This post is that line, expanded.

Here’s the gap it fills. vLLM is excellent at running a model on one server, or on a handful of GPUs inside one server. But nobody serves a real product from one server. You run dozens or hundreds of replicas, they come and go as traffic changes, some of them are prefill specialists and some decode, and the whole thing almost always lives on Kubernetes, because that’s where companies run everything else. And Kubernetes, for all its strengths, was built for web services, where every pod is interchangeable and every request costs about the same. An LLM fleet breaks both of those assumptions, badly.

llm-d is the open-source project that sits between the two. It doesn’t replace vLLM, and it doesn’t replace Kubernetes. It adds the missing layer: a router that understands KV caches and load, queuing that understands tenants and priorities, the plumbing to split one request across a prefill GPU and a decode GPU, a cache that spills beyond GPU memory, and autoscaling driven by signals that actually mean something for an LLM. It was started in May 2025 by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA, joined the CNCF as a sandbox project in March 2026, and is at version 0.10 as I write this.

I’ll go through it the way a request does, from the moment it hits the cluster to the moment its last token streams out, and then zoom out to how the fleet itself grows and shrinks. Here’s the route:

Part 1: Why Kubernetes Needs Help

What Kubernetes Gets Right

If you haven’t used it, Kubernetes is the system most companies use to run software across a cluster of machines. You describe what you want (run eight copies of this container, each with one GPU) and Kubernetes makes it so: it places the containers, called pods, onto machines, restarts them when they crash, replaces them when a machine dies, and rolls out new versions without downtime. A Service gives a group of identical pods one stable address and spreads traffic across them. An autoscaler adds or removes pods when some metric, usually CPU utilisation, crosses a threshold.

For a web API this is close to perfect, and it’s why GPU clouds and companies serving models standardised on it. The scheduling, failure handling, rollouts and observability are all solved problems you get for free. Nobody wants to rebuild that just because the workload is a language model.

Where It Goes Wrong for LLMs

The trouble is that a Service is built on two assumptions, and an LLM fleet violates both:


Kubernetes is great at running pods. It’s the part that chooses between them that doesn’t understand LLMs.

The first assumption is that pods are interchangeable. A Kubernetes Service picks a pod at random or in rotation, which is fine when any pod can serve any request equally well. But as I covered in the last post, every vLLM pod holds a different KV cache, full of prefixes from the requests it happened to serve. Send turn five of a conversation to the pod that served turns one to four, and its prefill is nearly free. Send it anywhere else, and thousands of tokens get recomputed from scratch. The pods look identical from the outside and are completely different on the inside.

The second assumption is that requests cost about the same. A “hi” with a ten-token answer and a 50-page document with a long summary differ in cost by a factor of a thousand or more, and nobody knows the output length in advance. Counting requests, which is what round robin effectively balances, says almost nothing about load.

Then there’s scaling. The default autoscaler watches utilisation, and for a GPU running continuous batching, utilisation is close to 100% whether the pod is comfortably busy or drowning in a queue forty requests deep. It’s the wrong signal entirely. I’ll come back to that in Part 7.

What you actually want is a load balancer that looks inside each pod before deciding: which one already holds this request’s prefix, which one has room in its KV cache, which one has a short queue, and, if prefill and decode run on different pods, which pair to use. That’s the core of llm-d.

What llm-d Is

llm-d is a stack of components that sits on top of model servers and inside Kubernetes. The model servers do the actual inference: vLLM by default, with SGLang and TensorRT-LLM also supported. llm-d handles everything above them. The project draws itself like this:


The whole stack: a router in front, model servers in an inference pool, caching between and below them, and controllers that deploy and scale them. Diagram: llm-d project, Apache 2.0

Reading top to bottom: requests come in through the llm-d Router, which is a standard proxy plus a component called the Endpoint Picker (EPP) that makes the routing decisions. Behind it is an inference pool of model server pods, which may be split into roles such as prefill and decode. Between and below the pods is a layer of KV cache management, which moves cache blocks between pods and spills them to CPU memory or storage. On the right, workload controllers deploy multi-node groups of pods, and an autoscaler adjusts how many there are. At the top left, a batch path feeds low-priority offline work into the same pool.

The project organises its advice as well-lit paths: tested, benchmarked recipes for common setups. The starting point is the optimized baseline, which is just intelligent routing in front of ordinary vLLM pods. The others add tiered prefix caching, prefill/decode disaggregation and wide expert parallelism. You only adopt the pieces your workload needs. That modularity is one of the design decisions I like most about it, so let’s take the pieces one at a time, starting with the router.

Part 2: The Router

The Gateway API and the InferencePool

llm-d doesn’t write its own proxy. Proxies are hard to get right (TLS, connection handling, HTTP/2, retries, observability), and excellent ones already exist. Instead it builds on the Kubernetes Gateway API, the modern, standard way to describe how traffic enters a cluster, and a Kubernetes SIG project on top of it called the Gateway API Inference Extension. That extension adds one key resource, the InferencePool:

An InferencePool is to LLM pods what a Service is to web pods, with one crucial difference: it names an endpoint picker that must be consulted for every request. The selector says which pods are in the pool, so as pods come and go, the pool’s membership updates automatically. The failureMode decides what happens if the picker itself stops answering: FailClose (the default) rejects requests, FailOpen lets the proxy fall back to ordinary balancing so the service degrades instead of failing.

It helps to separate the two paths through the system, which the project’s own diagram does nicely:


Dashed lines configure things once; solid lines carry every request. The EPP and the proxy scale independently. Diagram: llm-d project, Apache 2.0

On the control path, a gateway controller (Istio, agentgateway, Envoy AI Gateway, or a managed one such as Google Cloud’s load balancer) reads the InferencePool, finds the EPP, and configures the proxy to call it. The EPP reads the same pool to find the model server pods and starts probing their metrics. On the data path, each request goes client → proxy → EPP (for a decision) → proxy → the chosen pod. There’s also a standalone mode, with llm-d’s own Envoy deployed alongside the EPP, for clusters without Gateway API infrastructure.

ext-proc: How the Proxy Asks

The way the proxy “asks” is a protocol from Envoy called external processing, or ext-proc. When a request arrives, the proxy parks it and streams its headers and body to an external gRPC service, which can inspect them, modify them, and tell the proxy what to do next. For llm-d, that external service is the EPP, and the answer it sends back is a header, x-gateway-destination-endpoint, holding the IP and port of the pod that should get the request. The proxy then forwards the request there, exactly as if it had picked the pod itself.

This split is the clever part of the design. The proxy stays a fast, battle-tested data plane that knows nothing about LLMs. All the LLM-specific intelligence lives in the EPP, which can be written, tested and upgraded separately, and swapped between proxies, because the protocol between them is a standard. The cost is an extra network hop and some milliseconds of decision time per request, which is small next to a prefill that takes tens or hundreds of milliseconds, but it’s why the EPP’s own performance is something the project measures carefully.

Inside the EPP

The EPP is where llm-d’s routing actually happens. It’s a pipeline:


Every request passes through three stages; a fourth component keeps the picture of the pool up to date in the background. Diagram: llm-d project, Apache 2.0

Request handling parses the request (an OpenAI-style HTTP call, or vLLM’s own gRPC format) into an internal form, so everything after it is independent of the wire protocol. Flow control, if enabled, decides when the request may be dispatched at all, which is Part 4. Request scheduling decides where it goes, which is Part 3. And in the background, the data layer keeps the EPP’s view of the world current: it watches the Kubernetes API for pods joining and leaving the pool, scrapes each model server’s metrics (queue length, running requests, KV cache usage) on a short interval, and maintains structures like the prefix cache index we’ll meet shortly.

Everything here is a plugin. Parsers, filters, scorers, pickers, saturation detectors, fairness policies: each is an interface with several implementations, and a YAML file decides which ones run. That’s how one EPP binary serves a simple pool, a disaggregated pool, and a multi-tenant pool with very different behaviour.

Part 3: Choosing a Pod

Filter, Score, Pick

The scheduler inside the EPP runs a three-step pipeline for every request. Filters remove pods that can’t or shouldn’t serve it: unhealthy ones, ones with the wrong role (a decode pod for a prefill job), ones without enough latency headroom. Scorers give every remaining pod a number between 0 and 1 for some property: how much of the prompt it already has cached, how much KV cache it has free, how short its queue is. Each scorer has a weight, and a pod’s final score is the weighted sum. A picker then chooses, usually the highest score, sometimes a weighted random draw so that one pod doesn’t get every request during a burst.

A set of filters, weighted scorers and a picker is a scheduling profile. The project’s recommended production profile looks like this:

Three numbers, and they encode the central tradeoff of LLM routing from the last post: cache locality against load balance. Here’s how they play out for one request and three pods:


Cache affinity usually wins, until the pod holding the cache gets too busy. The weights decide where that line is.

Pod A holds most of the prompt in its cache, so it wins despite being moderately busy: its prefill will be nearly free. But if A’s queue fills up, its queue score collapses, and pod B, cold but idle, edges ahead. That’s exactly the behaviour you want. A router that always chases cache hits creates hot spots, because popular prefixes pile onto whichever pod cached them first. A router that only balances load throws the cache away. The weights are the dial between the two, and llm-d’s benchmarks show how much the dial is worth: in a production deployment on AMD MI300X GPUs, prefix-cache-aware routing gave three times the output throughput and half the time to first token compared with round robin.

There are more scorers for other situations. A session affinity scorer pins a session to the pod that served it before. A LoRA affinity scorer prefers pods that already have the requested fine-tuned adapter loaded. A token load scorer counts in-flight tokens rather than requests, which is a much better measure of how busy a pod really is. And there’s a subtle one called no-hit-LRU: for a request with no cache hit anywhere, it prefers the pod that has gone longest without receiving a cold request. Cold requests mean full, expensive prefills, so this spreads that heavy work evenly instead of letting it pile up on one unlucky pod.

Knowing Where the Cache Is

The prefix cache scorer raises an obvious question: how does the EPP know what’s in each pod’s cache? It’s not in the pod’s metrics, and it changes every few milliseconds. llm-d has two answers, and the difference between them is a lovely little systems tradeoff:


The approximate index remembers its own decisions. The precise index listens to what the pods actually did.

The approximate approach needs nothing from the model servers. The EPP cuts the prompt into chunks of about 64 tokens (estimated from character counts, since it doesn’t run a tokenizer), hashes each chunk together with the hash of the chunk before it, so each hash identifies the entire prefix up to that point, the same trick vLLM’s own prefix cache uses, and records in a local LRU table which pod it sent each prefix to. Later requests are scored by how many of their leading hashes point at each pod. It’s cheap and self-contained. Its weakness is that it only knows what it sent, not what the pod kept. If a pod evicts a prefix under memory pressure, the EPP keeps routing to it, and the request finds a cold cache.

The precise approach asks the pods. vLLM (and SGLang) can publish a stream of KV events over ZeroMQ: BlockStored when a block of keys and values is created, with its hash and the hash of its parent, BlockRemoved when one is evicted, and AllBlocksCleared when a pod drops everything. The EPP’s KV-cache indexer subscribes to every pod’s stream and maintains a global index from block key to the pods (and memory tiers) that hold it. To compute matching keys, it tokenises prompts exactly, using vLLM’s own tokenizer through a small render endpoint, so its hashes are identical to the ones the pods compute. There’s one more neat detail: between the moment the EPP routes a request and the moment the pod’s BlockStored event arrives, there’s a blind spot, so the indexer adds speculative entries the instant it routes, and lets the real events confirm or remove them.

The precise index costs more machinery: a tokenizer sidecar, network connections to every pod, and engine support for events. In exchange, it’s exact, it handles eviction, it knows about blocks offloaded to CPU memory, and it can tell apart two prompts with identical text but different images. As caches get more complicated, that accuracy matters more and more.

Predicting Latency Instead of Guessing

Weighted scorers have a weakness: the right weights depend on the workload, and workloads drift. Optimising time to first token favours consolidating requests onto warm caches; optimising time per output token favours spreading them out. A fixed set of weights is right for one traffic mix and wrong for the next.

llm-d’s answer is the most ambitious part of the router: learn the answer instead. A latency predictor runs as a set of sidecars next to the EPP:


A training server learns from every completed request; prediction servers answer “how fast would this pod serve this request?” on the hot path. Diagram: llm-d project, Apache 2.0

A training server continuously fits gradient-boosted tree models (XGBoost) on completed requests, mapping a pod’s state and a request’s features (prompt length, cache hit, queue depth and so on) to the TTFT and TPOT that were actually observed. Prediction servers load the latest models and, for each incoming request, predict how fast every candidate pod would serve it. The scheduler can then route on predicted headroom against a per-request latency target, and even refuse requests that no pod could serve in time. Google reported a 40% reduction in both TTFT and inter-token latency against the hand-tuned heuristics. It’s routing as a learned function rather than a formula, and I find it a genuinely elegant idea: the system measures its own consequences and adjusts.

Part 4: Flow Control

Why Queue at the Gateway?

So far the EPP decides where a request goes. Flow control decides when, and whether it should wait. That sounds like a minor detail until you look at what happens without it.

Traditional API gateways protect backends with rate limits in requests per second, which assumes requests cost about the same. For LLMs that assumption fails, so static limits are either too strict (idle GPUs) or too loose (overload). And if the gateway just forwards everything, requests pile up in each pod’s local queue, which creates three problems. The first is scheduling regret: once a request sits in a pod’s queue, it’s stuck there, even if a better pod frees up a second later. The second is priority inversion: the model server batches by arrival order, so a real-time chat request can wait behind a large offline job. The third is the noisy neighbour: one tenant sending huge prompts can fill every pod’s KV cache and starve everyone else.

llm-d’s fix is to hold requests in the EPP instead, in policy-aware queues, and only dispatch when the pool actually has room. The project’s diagram shows the idea:


Requests carry a tenant ID and a priority; when the pool is saturated, the EPP decides who goes next. Diagram: llm-d project, Apache 2.0

Three Decisions, In Order

Every request carries a flow key: a fairness ID (usually the tenant, from a header) and a priority (from an InferenceObjective resource the request names). Each flow key gets its own queue, and dispatch is three decisions in strict order:


Strict priority between bands, fair rotation between tenants, and a gate that only opens when the pool has room.

Priority comes first and is absolute: the highest band with waiting work is always served first, so batch jobs only ever use capacity that interactive traffic isn’t using. Fairness comes next: within a band, a pluggable policy, such as round robin, rotates between tenants, so one heavy tenant can’t monopolise the band. Ordering comes last: within one tenant’s queue, a policy picks which request goes, first-in first-out or something SLO-aware. Over all of it sits a saturation detector that reads the pods’ metrics and only lets requests through while the pool has spare capacity.

Holding requests centrally sounds like it would add latency, but it mostly moves the waiting from somewhere useless to somewhere useful. A request waiting in a pod’s queue is locked to that pod. A request waiting at the gateway can go to whichever pod frees up first, with full knowledge of every cache. One practical warning from the project’s docs that I appreciated: the tenant and priority headers must be set by a trusted gateway or auth layer, never by end users, or everyone will simply declare themselves premium.

Part 5: Splitting the Work Across GPUs

Prefill/Decode Disaggregation in llm-d

In the last post I described disaggregated serving: running prefill on one set of GPUs and decode on another, so that compute-bound prefills stop interfering with memory-bound decodes, and each pool can be sized and tuned for its own job. llm-d is one of the most complete open implementations of this, and it’s built as an extension of the same router.

Prefill and decode pods live in the same InferencePool, told apart by a label, llm-d.ai/role=prefill or llm-d.ai/role=decode. The EPP runs two scheduling profiles instead of one, and the order it runs them in is interesting. It picks the decode pod first, using the usual filters and scorers. Then a component called the decider looks at how much of the prompt that decode pod already has cached. If most of it is cached, there’s little prefill left to do, and sending it to a separate pod would cost more in transfer than it saves, so the request runs entirely on the decode pod. Only if a large uncached suffix remains does the EPP run the prefill profile and pick a prefill pod as well. Disaggregation becomes a per-request decision, not a fixed pipeline.

When both are picked, the flow goes like this:


The proxy sends the request to the decode pod; a sidecar there arranges the prefill and the KV transfer before decoding starts. Diagram: llm-d project, Apache 2.0

The proxy forwards the request to the decode pod, with the chosen prefill pod’s address in a header. A routing sidecar running next to the decode engine intercepts it, sends the prompt to the prefill pod with max_tokens=1 (do the prefill, produce one token, stop), and gets back metadata describing where the resulting KV blocks live. The sidecar then hands the request to the local decode engine along with that metadata. The decode engine pulls the KV blocks directly from the prefill pod’s GPU memory, the prefill pod frees them, and decoding begins. If the prefill pod returns a server error, the sidecar falls back to running the whole request on the decode pod.

Moving the Cache: NIXL and RDMA

The step that makes or breaks all of this is the transfer. llm-d uses NIXL, NVIDIA’s inference transfer library, which gives vLLM and SGLang one API over several transport backends (UCX, UCCL, libfabric) and networks (InfiniBand, RoCE, AWS’s EFA). The key property is GPUDirect RDMA: the network card reads the KV blocks straight out of one GPU’s memory and writes them straight into another’s, without touching either CPU or making an extra copy. vLLM’s KV cache is preallocated, so NIXL registers it with the network card once and transfers blocks in place.

Is the transfer worth it? Take Llama 3.3 70B with a 10,000-token prompt. Its KV cache is 320 KiB per token, so about 3.3 GB has to move. Over a single 400 Gb/s link (50 GB/s), that’s about 65 ms. The prefill itself is about 1.6 PFLOPs, which on four H100s at a realistic 60% of peak takes around 0.7 seconds. So the transfer costs about a tenth of the work it saves the decode pool, and modern GPU servers have several such links per node. Without RDMA, over plain TCP, the same transfer would be many times slower, which is why the docs are blunt that TCP is for development only.

The docs are equally honest about when disaggregation isn’t worth it. It pays off for long prompts with shorter outputs (their example is 10,000 input tokens to 1,000 output, not 200 to 200), for medium-to-large models, and for big mixture-of-experts models. The main tuning knobs are the ratio of prefill to decode pods and their parallelism: prefill wants many small replicas, decode wants fewer, wider ones. One of their recipes serves gpt-oss-120b, with 5,000-token prompts and 250-token answers, on 8 prefill pods with one GPU each and 2 decode pods with four GPUs each. Published results range from 10 to 30% more throughput on the same AMD hardware (Oracle) to 70% more tokens per second on NVIDIA B200s (AWS).

Wide Expert Parallelism

The biggest models push this further. Mixture-of-experts models like DeepSeek-R1 hold over 500 GB of weights, and, as I mentioned in the last post, their compressed MLA attention cache gets copied onto every GPU if you shard attention with tensor parallelism. The answer is wide expert parallelism: attention runs data-parallel (each GPU owns different requests and their KV caches, with no copies), while the expert layers are spread across many GPUs and many nodes, with tokens sent to whichever GPUs hold their chosen experts and back again. Those all-to-all exchanges are sparse, since each DeepSeek token visits only 8 of 256 experts, so they can run over InfiniBand or RoCE between nodes rather than needing NVLink everywhere.

In llm-d this combines with everything above:


Each role is one expert-parallel group spanning several nodes, deployed and restarted as a unit; the router picks a specific rank in each. Diagram: llm-d project, Apache 2.0

Prefill and decode each run as their own expert-parallel group, because mixing prefill and decode inside one group leaves ranks waiting on each other, and because the best all-to-all kernels differ for the two (DeepEP has a high-throughput mode and a low-latency mode). Each group spans several nodes, which raises a Kubernetes problem: a group is only useful if all of its pods are running. LeaderWorkerSet solves that. It’s a Kubernetes SIG workload API that treats a leader pod and its workers as one unit: scheduled all at once or not at all (gang scheduling), placed together inside one fast network domain, given rank identities, and restarted together if any member fails. On top of it, a DisaggregatedSet manages the prefill and decode groups as one versioned unit, so a rollout never pairs a prefill pod from the new version with a decode pod from the old one.

The router plays its part too. With data-parallel attention, every rank inside a pod has its own queue and its own KV cache, so llm-d treats each rank’s port as a separate endpoint and routes to a specific rank, not just a pod. The headline result from the v0.5 release: about 3,100 output tokens per second per B200 decode GPU, and 50,000 output tokens per second across a 16-by-16 B200 prefill/decode deployment.

Part 6: A Cache Bigger Than the GPU

Spilling Past HBM

Everything about prefix caching depends on one thing: the prefix still being in memory when the next request needs it. And GPU memory is small. Under real load, a pod’s KV cache turns over in seconds or minutes, so a user who pauses to read and then sends a follow-up often finds their conversation evicted, and pays for the whole prefill again.

The fix is the same one computer architecture has used for decades: a memory hierarchy. Below GPU memory, every server has a terabyte or two of CPU memory, below that local SSDs, and below that shared network storage. Each tier is bigger and slower than the one above:


Every tier below the GPU is slower than HBM, but even the slowest is faster than recomputing a long prefix.

The arithmetic is what makes this work. A 32,000-token conversation on Llama 3 70B holds about 10.7 GB of KV cache. Recomputing it means a prefill of about 6 PFLOPs, around 2.5 seconds on four H100s. Copying it back from CPU memory, split across the four GPUs’ PCIe links, takes around 50 ms. Even from shared storage over the network, it’s about a fifth of a second. Reading bytes beats redoing maths by a wide margin once prompts get long, which is exactly the “load vs recompute” tradeoff that the prefetching posts on this blog were about, just at a different layer.

In llm-d, offloading happens inside the model server, through vLLM’s KV connector interface. The simplest path is vLLM’s native offloading connector, which copies blocks to CPU memory in the background as they’re created, so evicting them from the GPU loses nothing:


Each pod keeps a second, much larger copy of its cache in CPU memory, and the router knows about it. Diagram: llm-d project, Apache 2.0

The same connector can tier further, to a shared filesystem or object store (a backend llm-d built and has since contributed upstream to vLLM), and third-party cache engines like LMCache, Mooncake and NVIDIA’s KVBM plug into the same interface. Because the precise indexer tracks which tier each block lives in, the router can send a request to a pod whose cache has the prefix in CPU memory, knowing it’ll be copied back far faster than it could be recomputed. The v0.5 release measured 13.9 times the throughput with hierarchical offloading at 250 concurrent users, compared with GPU memory alone, on four H100s.

Sharing Between Pods

The newest piece goes one step further. If the index knows that pod B has a prefix in its CPU tier, and pod A is the better choice for load, why should pod A recompute it? With peer-to-peer KV sharing, the router stamps the request with the source pod, and pod A pulls the blocks straight from pod B’s CPU memory over NIXL. Pod B’s GPU is never involved, so serving the copy costs it nothing, and if the blocks turn out to be gone, pod A simply falls back to computing them. At that point, the fleet’s caches stop being private to each pod and start behaving like one large shared cache, spread across every server in the cluster.

Part 7: Scaling the Fleet

Scaling on the Right Signal

The last piece is deciding how many pods there should be. As I said in Part 1, the default Kubernetes approach of scaling on utilisation doesn’t work here:


Continuous batching keeps the GPU busy at any load, so utilisation can’t tell a calm pod from a drowning one. Queues, KV usage and latency can.

So llm-d scales on what the router sees. The EPP already knows every pod’s queue, KV usage and in-flight tokens, and exports them as metrics. The recommended setup uses KEDA, a standard Kubernetes event-driven autoscaler, to read those metrics from Prometheus and adjust the replica count. There are four signals to choose from: queue depth per replica, a normalised pool saturation ratio that carries across hardware, token backlog (seconds of queued prefill work plus KV occupancy, which handles wildly varying prompt sizes), and estimated latency against the SLO, which turns autoscaling into a closed loop around the thing users actually feel. It can also scale a model all the way to zero when nobody is using it, which matters a lot when each idle replica is a GPU you’re paying for.

There’s an honest note in the project’s history here that I found instructive. Earlier versions had a much more ambitious workload variant autoscaler, a global optimiser that decided which model variants to run on which accelerators to minimise cost. In 2026 the project deprecated it in favour of the simpler KEDA approach, keeping a separate tool (Kueue) for sharing scarce GPUs between teams. Simpler and dependable beat clever and fragile. That’s a tradeoff I’d make too.

The hard limit on all autoscaling is cold start. Loading 140 GB of weights onto a fresh GPU takes minutes, not seconds, so you can’t scale up the instant a spike arrives. That’s why flow control and autoscaling are designed together: flow control absorbs the burst by queuing low-priority work at the gateway, while the autoscaler brings new pods up behind it.

Filling the Gaps With Batch Work

The final piece ties back to the economics from my last post: you pay for GPU-hours whether they’re busy or not. Interactive traffic has peaks and valleys, and the valleys are wasted money. llm-d’s batch gateway offers an OpenAI-compatible batch API for offline jobs (evaluations, document processing, synthetic data), and an async processor pulls those jobs from a message queue and feeds them into the same pool at low priority. Because flow control always serves the interactive band first, batch work soaks up exactly the capacity interactive users aren’t using, and disappears from the GPUs the moment they need it back. It’s the same idea as continuous batching filling idle slots in a step, applied to idle hours in a day.

Putting It Together

Follow one request through a full llm-d deployment. It arrives at a standard proxy, which parks it and asks the EPP over ext-proc. The EPP parses it, and flow control places it in the queue for its tenant and priority, dispatching it as soon as the pool has room and its band is up. The scheduler filters the pool to healthy pods with the right role, scores each one on how much of the prompt it already holds (from a precise index fed by the pods’ own KV events), on free KV memory and on queue length, and picks the best. If the prompt has a long uncached suffix, it also picks a prefill pod. The proxy forwards the request to the decode pod, whose sidecar arranges the prefill elsewhere and pulls the finished KV cache over RDMA. Decoding streams tokens back, the cache blocks are stored and offloaded to CPU memory, and the index hears about all of it, ready for the user’s next turn. Meanwhile, the autoscaler watches the same queues to decide whether the pool should grow, and batch work fills whatever capacity is left.

Each of those steps maps to an idea from the last post. Cache-aware routing is prefix caching made fleet-wide. Flow control is the scheduler’s admission and priority logic moved up to the gateway. Disaggregation and wide expert parallelism are the splits from the sharding section, made deployable. Tiered caching is PagedAttention’s blocks given a memory hierarchy. llm-d’s contribution isn’t any one new algorithm. It’s making all of them work together, on infrastructure companies already run.

Takeaway

Reading through llm-d’s design, what struck me most is where the performance has moved. In the CUDA post, speed lived inside a kernel: coalescing, tiling, tensor cores. In the last post, it lived inside one engine: batching, paging, scheduling. Here, a lot of it lives in a routing decision made before the request reaches any GPU at all. Three times the throughput from picking the right pod is a bigger win than most kernel optimisations ever deliver, and it comes from treating the cluster as one machine with a memory hierarchy, rather than a pile of independent servers.

I also like how much of llm-d is deliberately not new. It uses Envoy for proxying, the Gateway API for configuration, KEDA for autoscaling, LeaderWorkerSet for multi-node pods, vLLM for inference, and NIXL for transfers, and it contributes pieces back upstream when they’re useful to everyone. The new code is concentrated in the one place where LLM knowledge is needed, the EPP. That’s what makes it plausible as a standard rather than another platform to lock into, and it’s probably why so many companies that compete with each other are building it together.

And it fits where things are going. Agents and reasoning models generate longer contexts and more turns per task, which makes cache reuse across a fleet more valuable every year, not less. The router, the cache index and the memory tiers are going to matter more, and I think this is the layer where a lot of inference engineering will happen for the next few years.

That’s the full journey I wanted to take: from a single CUDA thread in Squeezing the SM, through one serving engine in Tokens at Scale-I, to a whole Kubernetes fleet here. And in Tokens at Scale-II, I go back inside a single engine, to how scheduling, batching and the paged KV cache actually work in vLLM.
