Tokens at Scale-II : Scheduling, Batching and the Paged KV Cache

2026-10-14

The GPU runs one step at a time. Everything interesting happens between the steps.


Cover photo: 极客湾Geekerwan via Wikimedia Commons, CC BY 3.0

In my first Tokens at Scale post, I walked the whole serving stack in one go, and batching got a few sections: static, dynamic, continuous, chunked prefill, and a paragraph on preemption. Then in my llm-d post I zoomed all the way out, to a fleet of servers behind a router. This part goes back down, into one engine, and into the small piece of code that I’ve come to think of as its heart: the scheduler.

Here’s why it deserves a whole post. Every forward pass vLLM runs is a decision the scheduler made a few milliseconds earlier: which requests run, and how many of each request’s tokens get processed. That one decision sets the throughput, the time to first token, how smoothly every answer streams, and how often requests get thrown out and recomputed. Change a single number in the scheduler’s configuration and every one of those moves. And unlike most of the machinery in an inference engine, the core of it is short enough to read in an afternoon.

So this is the “how and why” behind the batching sections of Part I, grounded in vLLM’s actual scheduler code (as of v0.31, October 2026). If you haven’t read Part I, the one idea to bring along is this: decode is memory-bound, so a step’s cost is mostly reading the weights once, and the more tokens share that read, the cheaper each one is. Here’s where we’re going:

Part 1: The Step Is the Unit of Work

Tokens, Not Requests

The first thing to get right is what a scheduler should even count. The natural guess is requests: run 64 requests per step, or 128. It turns out that’s the wrong unit, and the DeepSpeed-FastGen team at Microsoft showed why with a beautifully simple measurement. They timed a model’s forward pass while varying two things independently: the total number of tokens in the step, and how many separate requests those tokens came from:


A step’s time is set by how many tokens are in it. Whether those tokens come from one request or eight barely matters. Figure: Holmes et al. (2024), arXiv:2401.08671, CC BY 4.0

The four lines, for 1, 2, 4 and 8 requests, sit almost on top of each other. A step with 1,000 tokens costs about the same whether it’s one long prompt chunk or eight requests’ worth of mixed work. That’s exactly what Part I’s arithmetic predicts: the expensive work in a step is the weight matrices, and a weight matrix doesn’t care which request a row of its input came from. So a scheduler can be built around one number: how many tokens go into the next step. vLLM calls it the token budget.

The same paper has a second chart that tells you roughly how big that number should be:


With few tokens per step, the GPU is waiting on memory and throughput climbs with every token added. Past a few hundred, it’s compute-bound and flat. Figure: Holmes et al. (2024), arXiv:2401.08671, CC BY 4.0

This is the roofline from Part I, measured. On the left, a step has too few tokens to keep the tensor cores busy, so throughput grows almost linearly as tokens are added: each one is nearly free, because the weights are being read anyway. On the right, the GPU is saturated, and more tokens per step just mean longer steps. The knee sits at a few hundred tokens here. We’ll compute it for our own example in Part 3.

The FastGen authors pointed out one more consequence, and it’s a neat bit of maths. Because the throughput curve is concave (it bends downward), for any concave function f, 2·f(x) ≥ f(x + h) + f(x − h). In words: if you have 2x tokens to process over two steps, splitting them evenly gives at least as much throughput as any uneven split. So a good scheduler doesn’t just fill steps, it fills them evenly. Long prompts should be cut into pieces, and short ones combined, so every step lands near the same size. That’s the idea behind both FastGen’s Dynamic SplitFuse and vLLM’s chunked prefill, and it’s why a well-behaved server’s step times look almost flat.

How Requests at Different Positions Share One Step

Before looking at the scheduler, it’s worth seeing what the batch it builds actually looks like, because “batching requests together” hides a real problem. In one step, request A might be decoding its 813th token, request C might be halfway through its prompt, and request D might be on its 3,311th. Their inputs have different lengths, and each one needs to attend over a different amount of history. You can’t stack them into a neat rectangular tensor without padding, and padding is pure waste.

The solution, from the Orca paper and now used by every serving engine, is to flatten the batch:


All the tokens go into one long list. The linear layers see one matrix; only attention needs to know where each request starts and ends.

Every token being processed this step, from every request, goes into one long list. The linear layers (the QKV projection, the MLP, the output projection), which hold almost all the weights and FLOPs, run on that whole list as a single matrix, 9 rows in this example, maybe 2,000 in a real step. They don’t care about positions, so there’s no padding at all. Only attention has to treat requests separately, and it gets a small array of offsets (vLLM calls it query_start_loc) saying where each request’s tokens start in the list. The attention kernel uses those offsets, plus each request’s block table from PagedAttention, to make every token attend only to its own request’s history. A second small array, the slot mapping, tells the kernel where in the paged KV cache to write each new token’s keys and values.

This is the mechanical reason continuous batching works. Because nothing about the batch is rectangular, requests can join and leave between any two steps, and a step can mix one-token decodes with thousand-token prompt chunks freely. The scheduler’s only job is to decide what goes into the list.

Part 2: One Scheduling Step, in Code

No Phases, Just Catching Up

The most important design decision in vLLM’s scheduler is stated in a comment at the top of its schedule() function, written by Woosuk Kwon, one of vLLM’s creators. Paraphrasing: there is no “decoding phase” and no “prefill phase”. Each request has a number of tokens it knows about (its prompt, plus everything it has generated so far) and a number of tokens it has computed (whose keys and values are in the KV cache). At each step, the scheduler hands out tokens so that the computed count can catch up with the known count.

That one framing absorbs a surprising amount. A request that just arrived has thousands of known tokens and zero computed, so it gets a big chunk: that’s prefill. A request that’s generating has exactly one uncomputed token, the one it just sampled: that’s decode. A request whose prompt partly matched the prefix cache starts with a head start. A preempted request has its computed count reset to zero and simply catches up again. Even speculative decoding fits: the draft tokens are just extra known tokens to verify. There’s no special case for any of them.

Stripped of multimodal inputs, speculative decoding, KV transfer and the rest, the loop looks like this:

Here’s that loop filling a 2,048-token budget on a typical step:


Running requests are served first, in order; whatever budget is left goes to new arrivals, minus anything the prefix cache already holds.

A few details in this loop matter more than they look.

Running requests go first. Every decoding request gets its one token before any new prompt gets anything. This is what makes inter-token latency predictable: a flood of new arrivals can slow the step down (they add prefill tokens), but it can never skip anyone’s turn. The vLLM docs describe it as prioritising decodes, and it’s the main defence against the prefill stalls I described in Part I.

Admission is skipped entirely in a step that preempted someone. If the KV cache was so full that a running request had to be evicted, admitting a new request in the same step would just set up the next eviction. Holding off for a step lets memory settle. It’s a small rule that prevents a nasty failure mode called thrashing, where requests are admitted and evicted in a loop and nobody makes progress.

Prefix cache hits are applied at admission. get_computed_blocks hashes the new request’s prompt block by block and returns how much of it is already cached. Those tokens count as computed before the request runs a single step, so only the remainder costs any budget. In the figure, a 3,000-token prompt with a 1,500-token cache hit costs 1,500 tokens of work instead of 3,000.

A request that can’t fit is skipped, not waited on. There’s a comment in the running-request loop pointing out that it uses continue rather than break when a request can’t be scheduled this step (because, say, its encoder budget is exhausted), so the scheduler deliberately doesn’t follow strict first-come first-served order there: later requests can still run. It’s a small, honest admission that strict fairness and full utilisation pull against each other.

The Knobs That Shape It

Three settings control almost all of this behaviour.

max_num_batched_tokens is the token budget per step. Its default depends on the GPU and how vLLM is launched: on an H100, the API server uses 8,192 and the offline LLM class uses 16,384; on GPUs with 160 GB or more, both use 16,384; on smaller GPUs, the server drops to 2,048. Part 3 is entirely about choosing this number.

max_num_seqs caps how many requests can be running at once: 1,024 on H100-class GPUs, 256 on smaller ones. It’s a ceiling on the batch, independent of tokens. In practice, the KV cache usually runs out well before this cap is reached, but it stops the scheduler from admitting a thousand tiny requests whose combined caches would then grow into a wall of preemptions.

long_prefill_token_threshold caps how many tokens a single request can take in one step. It exists to stop one huge prompt from swallowing the entire budget, so several prompts can make progress side by side. The current code adds two thoughtful refinements: the cap is switched off when only one request exists (there’s nobody to starve), and in adaptive mode it never drops below an even share of the budget, budget divided by the number of requests.

Part 3: Choosing the Token Budget

The Free Zone

The token budget is the single most consequential setting in the scheduler, because it trades two things users feel directly. A small budget means short steps, so every streaming user gets their next token quickly, but new prompts trickle in a few hundred tokens at a time. A large budget means prompts get through fast, but every step that carries a big prefill chunk makes every decoding user wait for it.

To see where the balance falls, let’s reuse Part I’s simple model: Llama 3 8B on an H100, with 64 users decoding at 2,048 tokens of context each. A step’s time is the longer of its compute time (about 0.016 ms per token at the H100’s peak) and its memory time (about 9.9 ms, mostly reading the weights plus those 64 users’ KV caches). Now an 8,192-token prompt arrives, and we ask how the budget changes things:


Up to about 600 tokens per step, prefill tokens cost decoding users nothing. Past that, time to first token barely improves while everyone’s stream slows down.

The shaded region on the left is what I’ve been calling the free zone. A step is bound by memory at 9.9 ms whatever its token count, until the compute time catches up, at about 9.9 ÷ 0.016 ≈ 600 tokens. Below that, the 64 decode tokens use 64 of them, and up to roughly 550 prompt tokens can ride along for free: the weights are being read anyway, and the tensor cores have the spare time. Decoding users see no slowdown at all.

Past the free zone, every extra token makes the step longer, and every decoding user’s inter-token latency grows with it: about 33 ms at a budget of 2,048, 133 ms at 8,192. Meanwhile, look at the time to first token for that 8K prompt. It improves dramatically from 256 to about 1,024, because prefill throughput is climbing up the curve toward the compute roof. Beyond that it barely moves, from about 142 ms to about 134 ms, because the GPU is already doing prefill as fast as its tensor cores allow. Going from 1,024 to 8,192 buys the new user eight milliseconds and costs all 64 existing users more than a hundred.

These are idealised numbers (real kernels run perhaps 1.5 times slower, and the knee moves with the model, the GPU and the context lengths), but the shape is the point, and it matches what the vLLM docs advise: smaller budgets such as 2,048 for better inter-token latency, larger ones such as 8,192 or more for throughput. The default of 8,192 on an H100 server leans toward throughput. If your users care about smooth streaming more than about the last few milliseconds of time to first token, a budget just past the knee, around 1,024 to 2,048 in this example, is a much better place to stand.

The Hidden Costs of Chunking

Chunked prefill looks free in that picture, but it isn’t quite. Three costs are worth knowing about.

The first is re-reading earlier chunks. When a prompt is split into chunks, each chunk’s attention has to read the keys and values of every chunk before it. An 8K prompt in 1,024-token chunks means chunk 8 reads 7,168 tokens of cache, chunk 7 reads 6,144, and so on: 28 chunks’ worth of extra reads in total, about 3.5 GiB for Llama 3 8B. At 3.35 TB/s that’s about a millisecond spread over eight steps, which is negligible next to the 130-odd ms of compute. But it grows with the square of the prompt length divided by the chunk size, so it matters more for very long prompts, tiny chunks, and models with full multi-head attention, whose caches are four times bigger.

The second is tile quantisation, an old friend from the CUDA post. The matrix multiplies inside a step work on tiles, typically 128 rows at a time. A step of 1,024 tokens is exactly 8 tiles. A step of 1,025 tokens needs 9 tiles, and the ninth is almost entirely padding: that’s about 11% of the step’s tensor-core work spent on nothing. So budgets and chunk sizes are best chosen as multiples of the tile size, which is one reason the defaults are all powers of two.

The third is per-step overhead. Every step costs some fixed CPU time: running the scheduler, preparing input tensors, launching kernels. Smaller chunks mean more steps per prompt, and more of that overhead. This is a big part of why vLLM works so hard to hide that CPU time, which is Part 6.

Part 4: When Memory Runs Out

Why Preemption Happens

The scheduler admits requests without knowing how long their answers will be. It can’t: nobody knows that until the model emits its end-of-sequence token. So admission is optimistic. It checks that there’s room for the request’s prompt and next few tokens, not for everything it might eventually generate. Meanwhile, every running request’s cache grows by one token per step, and with hundreds running, memory fills steadily. Eventually, allocate_slots asks for a block and there isn’t one.

At that point, the scheduler has to free memory by evicting someone, and the code makes the choice depend on the scheduling policy. Under first-come first-served, it pops the last request in the running list, the one admitted most recently, on the reasoning that it has made the least progress and losing it wastes the least. Under priority scheduling, it evicts the running request with the least important priority, breaking ties by latest arrival:


Optimistic admission eventually runs out of memory; preemption is the safety valve that lets the scheduler be optimistic in the first place.

What preemption does is blunt. The request’s KV blocks are freed, its computed-token count is reset to zero, its status becomes PREEMPTED, and it goes back to the front of the waiting queue, so it’s the first in line to come back. The loop keeps evicting, newest first, until the allocation succeeds or there’s no one left to evict.

Recompute or Swap?

When the evicted request comes back, its cache has to be rebuilt. There are two ways to do that. Swapping copies the cache to CPU memory on eviction and back on return. Recomputation throws it away and runs prefill again over the prompt and everything generated so far. Early vLLM supported both; the V1 engine uses recomputation only, and the docs say why: it has lower overhead in V1’s architecture.

The arithmetic is closer than you might think. Take a request with 4,096 tokens of context on Llama 3 8B: its cache is about 0.5 GB. Swapping it out and back in over PCIe 5 at a realistic 55 GB/s or so takes about 20 ms in total, plus the bookkeeping of managing CPU memory and keeping copies in sync with the GPU’s schedule. Recomputing it is a 4,096-token prefill, about 66 TFLOPs, around 70 ms at peak and more in practice. On paper, swapping wins.

But two things tip it toward recomputation in practice. The recompute doesn’t happen in isolation: the returning request’s prompt is chunked into ordinary steps alongside everyone’s decodes, so much of it rides in the free zone from Part 3. And the bigger factor is something I found in vLLM’s block pool code. When a request is freed, its blocks aren’t wiped. With prefix caching on, every full block that has a hash goes to the back of the eviction queue with its contents intact. So when the preempted request returns, get_computed_blocks finds many of its own blocks still sitting in the cache, and they count as computed instantly. Only the blocks that were actually reused by someone else in the meantime need recomputing. Preemption with recomputation, in V1, is often much cheaper than it sounds.

It’s still not free. A preempted request loses its place in the stream, and its user sees a pause, so frequent preemption shows up directly in tail latency. vLLM logs a warning each time and exports a counter for it, and the docs’ advice is what you’d expect from the physics: give the KV cache more memory (raise the GPU memory utilisation, or split the model over more GPUs), or admit less work at once (lower max_num_seqs or the token budget).

Part 5: Who Goes First

FCFS and Priority

The waiting and running queues come in two flavours in vLLM:


First come first served is simple and predictable. Priority lets important traffic jump the queue, and changes who gets evicted.

First-come first-served (FCFS), the default, is a plain double-ended queue: requests are served in arrival order, and a preempted request is pushed back onto the front. Its weakness is head-of-line blocking. If a 30,000-token prompt is at the front of the queue, it gets first claim on the budget, and three requests that just say “hi” sit behind it. Chunked prefill and the per-request cap soften this a lot, since the big prompt can’t take more than its share of any step, but under FCFS short requests still wait for long ones that arrived first.

Priority scheduling replaces the queue with a heap ordered by a priority number the client sends with each request (lower is more important), then by arrival time. Interactive chat can be priority 0 and an overnight evaluation job priority 9, and the scheduler will always admit the chat first. It also changes preemption: instead of evicting the newest request, the scheduler evicts the least important one, so a batch job gets thrown out before a user’s conversation does.

What neither policy provides is fairness between users. Nothing stops one customer from sending a thousand requests and filling the queue. That’s deliberately left to the layer above, which is exactly what llm-d’s flow control does at the gateway with its tenant queues, as I described in the last post. The engine schedules tokens; the gateway schedules people.

The Job Length Nobody Knows

Anyone who has studied operating systems will notice what’s missing. The classic answer to head-of-line blocking is shortest job first: run the short jobs before the long ones, which provably minimises average waiting time. An LLM scheduler can’t do that directly, for a reason that’s specific to autoregressive generation: it knows how long a prompt is, but not how long the answer will be. A short question can produce a 2,000-token essay.

This is an active research area, and two ideas from it stand out. FastServe (Wu et al., 2023) borrowed the multi-level feedback queue from classic OS schedulers: every request starts in a high-priority queue and is demoted as it runs longer, so short jobs naturally finish first without anyone predicting their length. More recently, learning to rank (Fu et al., 2024) trains a small model to predict not the exact output length, which is hard, but the relative order of output lengths across waiting requests, which turns out to be much easier and is all a shortest-job-first scheduler needs. Both report big improvements in latency, and both trade a little predictability for it. I like that the field keeps rediscovering scheduling theory from the 1960s and 70s, adapted to a new kind of job.

Part 6: Around the Scheduler

The Persistent Batch

The scheduler’s output each step is just a description: which requests, how many tokens each, which new KV blocks. Turning that into GPU tensors (token IDs, positions, block tables, the offsets for attention) is the model runner’s job, and doing it from scratch every step would be wasteful, because consecutive steps are almost identical. Most requests in step N+1 were in step N.

So vLLM keeps a persistent batch: the input tensors live from step to step, and each step applies only the difference:


Requests join and leave by editing rows in place. Most of the batch is reused untouched from the step before. Diagram: vLLM project, Apache 2.0

When request D joins, it gets a new row. When request A finishes, D’s row is moved into A’s slot so the table stays compact. Everything else is left alone, and only the new tokens are written. This is continuous batching at the data-structure level: the batch isn’t rebuilt each step, it evolves.

Async Scheduling

Even with the persistent batch, each step has CPU work: running the scheduler loop, preparing the inputs, and processing the outputs. For a small model, a decode step might take only 5 to 10 ms on the GPU, and if the CPU work runs between steps, the GPU sits idle for that time. On fast GPUs with small models, that idle time can be a noticeable fraction of the total.

Async scheduling overlaps the two. While the GPU executes step N, the CPU is already scheduling and preparing step N+1:


The CPU always works one step ahead, so the GPU goes straight from one step to the next. Diagram: vLLM project, Apache 2.0

There’s a wrinkle that I found really neat in the code. To schedule step N+1, the scheduler needs to know each request’s next token, but that token is being sampled on the GPU in step N and doesn’t exist yet. So the scheduler uses placeholders: it counts the not-yet-known tokens as already computed (num_output_placeholders in the code), schedules the step as if they were there, and lets the GPU fill in the real token IDs when it starts step N+1. The cost is some extra care at the edges. For instance, the scheduler must avoid scheduling one step too many for a request that might have just hit its maximum length, and you can see exactly that check in the running loop.

CUDA Graphs and Padded Batches

The last piece is about kernel launches. A decode step for a model of any real size involves hundreds of small kernels, and launching each one from the CPU costs a few microseconds. Together that can add up to a millisecond or more per step, a real fraction of a 10 ms decode step. As I covered in the CUDA post, CUDA graphs fix this by recording the whole sequence of launches once and replaying it with a single call.

The catch is that a CUDA graph is recorded for fixed tensor shapes. vLLM therefore captures graphs for a set of batch sizes at startup, and at run time it pads each step’s batch up to the nearest captured size. A step with 37 decoding requests might run as a 40-token graph, with three wasted rows. It’s another small cost the scheduler indirectly controls, and a reason step sizes that land on round numbers run slightly better. At its default optimisation level, vLLM uses full graphs for uniform decode steps and piecewise graphs for mixed steps, where attention, the one part whose shape varies with each request’s context, runs outside the graph and everything else runs inside it.

Part 7: One Layer Down: The Paged KV Cache

Every step, the scheduler calls two functions on the KV cache manager: get_computed_blocks to find what’s already cached, and allocate_slots to find room for new tokens. This last part opens those up, because the memory underneath the scheduler is where PagedAttention and prefix caching actually live.

The Block Table and the Slot Mapping

Part I introduced PagedAttention as virtual memory for the KV cache: fixed-size blocks, a block table per request, and no more reserving memory for answers that may never be written. Here’s what that looks like at the level of a single token:


A token’s address is two lookups and a multiply. Inside a block the cache is contiguous; between blocks it can be anywhere.

Every layer’s KV cache is one big preallocated tensor, divided into blocks of 16 tokens by default. A request’s block table is just a list of physical block numbers, one per 16 tokens of context. To find where token 37 lives, divide its index by 16 to get the logical block (2), look that up in the block table (11), and add the remainder: slot 11 × 16 + 4 = 180. The same block table works for every layer, because every layer stores the same tokens in the same positions of its own tensor.

That calculation happens twice per token per step, on two different paths. On the write path, the model runner builds the slot mapping I mentioned in Part 1, one slot number per new token in the flattened batch, and a small kernel (reshape_and_cache_flash in vLLM) scatters each token’s new keys and values into those slots, in every layer. On the read path, the attention kernel receives each request’s whole block table and walks it block by block.

Block tables in V1 are append-only: a running request only ever adds entries at the end, never rewrites old ones. That makes it cheap to keep them in the persistent batch from Part 6 (a new block is one new number in a row), at the cost of an occasional duplicate block that I’ll come back to.

The Kernel That Reads a Scattered Cache

The original vLLM paper came with its own CUDA kernel, PagedAttention, written specifically to read keys and values through a block table. It worked, but it cost something: the paper measured the attention kernel itself running 20 to 26% slower than the best contiguous kernel of the time. vLLM’s own docs now describe that kernel as historical. Today, the attention backends that vLLM uses by default, FlashAttention (version 3 on Hopper, 4 on Blackwell, 2 elsewhere) and FlashInfer, support paged KV caches natively. You pass them the block table, and they handle the rest.

The reason the overhead mostly disappeared is a nice lesson from the CUDA post. A FlashAttention kernel already works in tiles: it loads a tile of keys and values into shared memory, computes against it, and moves on to the next. With a paged cache, the only change is where each tile comes from. Instead of “the next 16 rows of one big array”, it’s “row block_table[i] of the pool”. Within a block, the 16 tokens’ keys for one head sit next to each other, 16 × 128 × 2 bytes = 4 KiB contiguous, which is plenty for fully coalesced loads. The indirection costs one extra lookup per tile, not per element, so it hides in the noise. For decode, where attention is memory-bound anyway, what matters is that every block is read exactly once per step, and that’s the same paged or not.

How Prefix Caching Finds a Match

Now get_computed_blocks. When a request arrives, how does vLLM know which of its blocks are already sitting in the cache? It hashes them. Each full block gets a hash computed from three things: the hash of the block before it, the token IDs in the block, and any extra keys that change what the block means, such as the LoRA adapter, image hashes for multimodal prompts, or a per-tenant salt. Because each hash includes its parent’s, a block’s hash identifies the entire prefix up to the end of that block, not just its own 16 tokens. Since v0.11 the default hash is SHA-256, so collisions are not a practical concern.

The lookup is then a walk: hash block 0, look it up in a dictionary from hash to block; if it’s there, hash block 1 using block 0’s hash as its parent, look that up, and so on, stopping at the first miss. vLLM’s design docs have a worked example with a block size of 4, where request 0 has been running for a while and request 1 arrives sharing its first 10 tokens:


Request 1 shares 10 tokens with request 0 but only hits two blocks: its third block holds IJkl, not IJKL, so the hash differs. Diagram: vLLM project, Apache 2.0

Two details jump out. First, request 1 matches 10 tokens of request 0’s prompt but gets credit for only 8: its third block contains IJkl, which hashes differently from request 0’s IJKL, so the walk stops there. Matching works in whole blocks, so the last partial block of any shared prefix is always recomputed. Second, only full blocks are ever hashed: request 0’s block 4 (QR) has no hash yet and can’t be matched until it fills. The block size is a tradeoff between this matching granularity and the per-block bookkeeping overhead, and 16 is the compromise vLLM settled on.

The salt deserves a word, because it’s a security feature hiding in a performance one. If two tenants share a prefix cache, one can learn something about the other’s prompts by timing: a fast first token means “someone recently sent this prefix”. Adding a cache_salt to a request mixes it into the first block’s hash, so only requests with the same salt can ever match each other’s blocks.

Reference Counts and the LRU Free Queue

The last piece is what happens to blocks over time. Every block has a reference count: how many running requests are using it. A cache hit “touches” a block: it increments the count, and if the block was sitting unused, takes it out of the free queue so it can’t be evicted while in use. That’s how two requests can share blocks 0 and 1 in the example above.

When a request finishes or is preempted, each of its blocks’ counts goes down by one, and blocks that reach zero go into the free queue, a doubly linked list whose pointers live directly inside the block objects so that moving a block is O(1) with no extra allocations. But they go in carefully:


Freed blocks go to the tail in reverse order, so a request’s last blocks, the least likely to be shared, are the first to be evicted. Diagram: vLLM project, Apache 2.0

Blocks are freed in reverse order, last block first. The logic is lovely: a request’s later blocks hash longer and more specific prefixes, so they’re the least likely to be reused by anyone else, and they should be evicted first. Its first blocks, holding the system prompt that every request shares, are kept the longest. And a freed block keeps its contents and its hash. It’s only truly evicted when it reaches the head of the queue and some allocation needs it, at which point its hash is removed from the cache dictionary and the block is reused. Until then, a returning request (including a preempted one, as in Part 4) can still find it.

One honest wrinkle comes from the append-only block tables. If two requests independently generate the same full block (say, the same prompt sampled greedily twice), the second one can’t swap its own copy for the first one’s, because that would mean rewriting its block table. So for a while, the cache holds a duplicate. The duplicate disappears when the request finishes. It’s a small memory cost paid for a simpler, faster data structure, and the vLLM docs say so plainly, which I appreciated.

Putting It Together

Follow a few steps of a busy vLLM server and the whole picture is there. Every few milliseconds, the scheduler starts with a token budget. It gives every running request its due first: one token to each decoder, a chunk to each prompt in progress, allocating KV blocks as it goes and evicting the newest request if memory runs out. Then, if no one was evicted, it admits waiting requests in priority or arrival order, skipping whatever the prefix cache already holds and capping any single prompt’s share. The result is a flat list of tokens from dozens of requests at wildly different positions, which the model runner turns into tensors by editing last step’s batch, while the CPU is already planning the step after. The GPU runs one forward pass over the whole list, every request gets its next token, and the loop goes round again.

Underneath, it’s the same physics as Part I. A step’s cost is set by its token count, not its request count, and the throughput curve is concave, so steps should be filled evenly and to about the knee. Prefill tokens below the knee ride free on decode’s weight reads; above it, they slow everyone down. Memory, not compute, is what eventually runs out, so the scheduler is optimistic and keeps preemption as its safety valve. And beneath all of it, the memory itself is paged: blocks found by hashing prefixes, written through a slot mapping, read through a block table, and evicted from the least shareable end first.

Closing Tokens at Scale

What surprised me most while reading through vLLM’s scheduler is how small the core idea is. Everything I’d thought of as separate machinery (prefill, decode, chunked prefill, prefix caching, preemption, even speculative decoding) collapses into one sentence: each request’s computed tokens catch up with its known tokens, a budget’s worth at a time. The complexity in the real file, which is over three thousand lines now, comes almost entirely from the features layered on top (multimodal inputs, KV transfer, pipeline parallelism), not from the scheduling itself. That’s the sign of a good abstraction, and it’s the kind of design I’d like to be able to come up with myself one day.

It also made the connection to operating systems feel very literal. A token budget is a time slice. The block table is a page table, the free queue is an LRU page cache, and the salt is process isolation. Preemption with recompute is killing a process and restarting it, made cheap by that cache. FCFS against priority against shortest-job-first is exactly the argument from every OS textbook, with one twist that’s new: nobody knows how long the job is. And the free zone is the roofline again, deciding in milliseconds how much of a prompt can ride along with everyone else’s decode for nothing.

This is where I’m ending Tokens at Scale. Part I walked the whole serving stack, from one prompt to thousands of users. My llm-d post took it out to a fleet of servers on Kubernetes. And this part went all the way into one engine, down to the step, the scheduling loop and the paged memory under it. Between the three, I’ve covered what I set out to understand when I started reading about inference engineering, and I hope they’re as useful to read as they were to write.

Further reading

If you only read a few things after this, make it these:

  • Yu et al. (2022), Orca: A Distributed Serving System for Transformer-Based Generative Models (OSDI): iteration-level scheduling and selective batching, where continuous batching started
  • Agrawal et al. (2024), Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve: chunked prefill, stall-free batching and how to pick the token budget
  • Holmes et al. (2024), DeepSpeed-FastGen: the token-count measurements in this post, and the concavity argument behind Dynamic SplitFuse
  • vLLM’s scheduler source and prefix caching design doc: start at schedule() and read the first two loops, then the doc’s worked example
